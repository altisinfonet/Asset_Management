# Asset Tracker API reference

The REST API of the Asset Tracker: how to call it, the conventions every endpoint follows, the permission model and a
catalogue of every operation. The same API serves the web app and, later, the mobile app.

- **Full schema (request and response bodies, every field):** `GET /v1/openapi.json` on any running API
  (for example `http://localhost:3000/v1/openapi.json` on the local stack). The source is
  [`engineering/openapi.yaml`](engineering/openapi.yaml), which is generated by
  [`engineering/tools/gen.mjs`](engineering/tools/gen.mjs) and never edited by hand.
- **Typed client:** `packages/api-client` is generated from the same file (`pnpm --filter @assettracker/api-client generate`).
- **Status of this page:** the tables for the endpoint catalogue and the problem codes are generated; everything
  else is written by hand from the code and the contract. Last refreshed against contract version `1.0.0-m2`
  (see [VERSION.md](VERSION.md)).

## 1. Base URL and versioning

- Every endpoint lives under **`/v1`**. Locally the API listens on `http://localhost:3000` (Docker Compose), so a call is
  `http://localhost:3000/v1/assets`. A cloud or self-hosted install uses its own host (`https://<host>/v1/...`); the
  tenant is **never** part of the URL, see section 2.
- Two orchestrator probes are served without the prefix and are not part of the contract: `GET /healthz` (liveness) and
  `GET /readyz` (readiness: database reachable and all migrations applied). `GET /v1/health` and `GET /v1/version`
  (build name, version, commit, role) need no credential. `GET /v1/openapi.json` serves the contract (cached for 5 minutes,
  `ETag`).
- Versioning: the URL carries the major version. Within `/v1` changes are additive (new endpoints, new optional fields,
  new problem codes), so clients must ignore unknown fields and fall back to the HTTP status for unknown problem codes.
  The contract document itself is versioned in `info.version` (today `1.0.0-m2`: milestones M1 and M2).
- Request and response bodies are JSON (`application/json`); errors are `application/problem+json`. Timestamps are RFC 3339
  UTC, dates are `YYYY-MM-DD`, money is `{ "amount_minor": 12999, "currency": "EUR" }` (integer minor units, ISO 4217).
  Ids are UUIDs generated by the server.

## 2. Authentication

There are two ways to authenticate. The **tenant is derived only from the credential**: a tenant id in a header, query
string or body is never read. An id that belongs to another tenant answers `404 not-found`, exactly like a missing one.

### 2.1 Browser session (cookie plus CSRF header)

Used by the web app. `POST /v1/auth/login` with `{ email, password }` (and `tenant_slug` when the email exists in more than
one tenant) creates a server-side session and sets the `__Host-at_session` cookie (`HttpOnly; Secure; SameSite=Lax; Path=/`).

- Every **mutating** request made with the cookie (`POST`, `PATCH`, `PUT`, `DELETE`) must send `X-CSRF-Token: <token>`.
  The token is returned by login, by MFA verification and by `GET /v1/auth/me`. A missing or wrong token is
  `403 csrf-invalid`.
- A session has an **idle timeout** (30 minutes by default, sliding) and an **absolute timeout** (12 hours by default);
  both are configurable per install and returned in `GET /v1/auth/me` (`session.idle_expires_at`,
  `session.absolute_expires_at`). A request on an expired or revoked session is `401 session-expired`.
- A user can list and end their sessions (`/v1/auth/sessions`); an administrator can end another user's sessions.
  A password reset, role change, disabling or archiving a user ends that user's sessions.

### 2.2 Bearer API keys

Used by scripts and integrations. Send `Authorization: Bearer <prefix>.<secret>`. No cookie and no CSRF header are needed.

- Created with `POST /v1/api-keys` (permission `apikey:manage`). The full key is shown **once** in the response; only its
  hash is stored. Keys have a name, scopes (`resource:action` permission strings), an optional expiry and can be revoked.
- A key can never exceed the permissions of the user that created it (scopes must be a subset of the creator's own).
- Self-service endpoints (`/v1/auth/sessions`, `/v1/auth/mfa/*`, marked "signed in (browser session)" in the catalogue) need
  a browser session, not an API key.

### 2.3 The sign-in and MFA flow

1. `POST /v1/auth/login` returns `{ status }`:
   - `authenticated`: the session cookie is set; the body carries `csrf_token` and the `user`.
   - `mfa_required`: no session exists yet. The body carries `mfa.challenge_id` and the allowed `mfa.methods`
     (today `totp` and `recovery_code`).
   - `tenant_selection_required`: the email exists in several tenants; call again with `tenant_slug` (the body lists the choices).
2. For `mfa_required`: `POST /v1/auth/mfa/verify` with `{ challenge_id, method, code }` (a 6-digit TOTP code, or one of the
   ten one-time recovery codes). A challenge is valid for 5 minutes with a few attempts; a wrong code is
   `401 mfa-invalid-code`, an expired one `401 mfa-challenge-expired`. On success the session is created and `csrf_token` returned.
3. **Enrolment** (`POST /v1/auth/mfa/enrol`, then `/enrol/confirm` with a first code) returns the secret and QR once and then ten
   recovery codes once. Regenerating recovery codes and turning MFA off need the **current password or a current TOTP code**
   in the body; a wrong value is `403 reauth-failed` (never 401, which clients treat as "session gone"). Turning MFA off is
   `403 mfa-required-by-policy` when the tenant enforces it. Administrators can reset another user's MFA.
4. **Tenant MFA policy.** When the tenant requires MFA for a user's role and the user has not enrolled, the session is
   _limited_: `GET /v1/auth/me` returns `mfa_enrolment_required: true` and every other endpoint except logout and
   `/v1/auth/mfa/enrol*` answers `403 mfa-enrolment-required` until enrolment is confirmed. `GET /v1/auth/me` also exposes the
   tenant's `mfa_policy` so a client can explain it up front.

### 2.4 Endpoints that need no credential

Login, MFA verify, password forgot and reset, `GET /v1/auth/password-policy`, invitation lookup and accept, `GET /v1/health`,
`GET /v1/version`, `GET /v1/openapi.json` and the two probes. The auth ones take no cookie and no CSRF header and are
throttled per IP and per account (section 3.7). Password-reset and invitation tokens are single use and stored hashed;
"forgot password" always answers `202` so it never reveals whether an account exists.

Password rules (read the live values from `GET /v1/auth/password-policy`): 12 to 128 characters, no composition rules,
Unicode NFKC-normalised, rejected when found in a breached-password list. A rejected password is `422 validation` with an
`errors[]` entry at `/password` (`too-short`, `too-long` or `breached`).

## 3. Conventions

### 3.1 Errors: problem+json

Every error is [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) `application/problem+json`:

```json
{
  "type": "https://api.assettracker.test/problems/validation",
  "title": "Validation failed",
  "status": 422,
  "code": "validation",
  "detail": "The request body failed validation.",
  "request_id": "5c1f0a52-...",
  "errors": [{ "pointer": "/asset_tag", "message": "is already in use", "code": "duplicate" }]
}
```

`code` is the stable machine-readable identifier (never renamed); `errors[]` appears for validation failures (JSON pointer,
or `query:<name>` / `path:<name>`); some conflicts add extension members, for example `usage` with counts of what blocks a
delete. The `type` base is configurable per install. Each error response in the contract lists the codes it can carry.

### 3.2 Optimistic concurrency: ETag, If-Match, 428 and 412

Every single-resource `GET` and every create or update response carries `ETag: W/"<version>"`. `PATCH` and `DELETE` (and the
other version-guarded operations marked "If-Match" in the catalogue) must send `If-Match` with that value:

- missing: `428 precondition-required`;
- stale (someone else changed it): `412 precondition-failed`. Re-read the resource, merge, retry.

Check-out, check-in and transfer accept an optional `If-Match` on the asset and also serialise on the server, so a lost race
shows up as `409` (`asset-already-checked-out`, `asset-not-checked-out`, `conflict`). Their responses return the
**updated asset** (with its new `ETag`) together with the assignment, so a client can chain the next call without a re-fetch.
The typed client never records or replays ETags for `POST` action paths.

### 3.3 Idempotency-Key

Every mutating request (`POST`, `PUT`, `PATCH`, `DELETE`) accepts an `Idempotency-Key` header: 8 to 255 printable ASCII
characters, client generated (a UUID is fine), unique per principal. It is **required** (`400 idempotency-key-required`
without it) on asset check-out, check-in and transfer, accessory check-out and return, consumable stock movements, label
batches, loaner check-out, quick check-out and quick return, and import commit; the catalogue marks
these with "Idempotency-Key" in the Requires column. Rules:

- Same key, same method, path and body: the stored response is replayed with the original status, `ETag` and `Location`, and
  the header `Idempotent-Replayed: true`. The handler does not run twice.
- Same key, different request: `422 idempotency-key-reuse`.
- Same key while the first request is still running: `409 idempotency-key-in-flight` (after a short wait of about 3 seconds).
- A request that fails is rolled back together with its claim on the key, so retrying the same key runs it again.
- Keys expire after 24 hours. Responses that carry a secret (MFA enrolment, recovery codes) are never stored for replay, so
  those operations take no key.
- A malformed key is `400 idempotency-key-invalid`.

### 3.4 Pagination (cursor)

List endpoints take `limit` (1 to 200, default 50) and an opaque `cursor`. The response is
`{ "data": [...], "page": { "next_cursor": "...|null", "has_more": true } }`. Pass `next_cursor` back as `cursor` to get the
next page. `page.total` is only returned with `include_total=true` because it costs a count. A cursor is bound to the `sort` and
filters that produced it; changing them or sending a garbled cursor is `400 invalid-cursor`: start again without a cursor.

### 3.5 Filters, sort, expand and sparse fields

- **Filters** are plain query parameters named in the contract (for the asset list, for example `status_id`, `state_type`,
  `category_id`, `model_id`, `location_id` with `include_sublocations`, `assigned`, `assigned_person_id`, `overdue`,
  `warranty_end_before`, `updated_since`, `archived`). Array filters are comma separated. Custom fields filter with
  `cf[<key>]=<value>`. `q` is a text search; `tag` and `serial` are exact lookups.
- **Sort** is a comma-separated list of the keys a list allows, `-` prefix for descending (`sort=-created_at,name`). A unique
  `id` tiebreaker is always appended so paging is stable.
- **Expand** (`expand=location,model`) embeds related objects under `expanded`; **fields** limits the response to named fields.
  Both are listed per endpoint in the contract.
- **Bulk** operations (for example `POST /v1/assets/bulk-update`, `bulk-archive`, `bulk-restore`, `bulk-move`) take up to
  100 items and answer `200` with a result per item in request order: `{ results: [{ index, status, data | error }], summary }`.
  The HTTP status is `200` whenever the request itself was well formed; read the item outcomes in the body. The loaner
  scan flows (`quick-checkout`, `loans/return`, pool `members/bulk-add` and `bulk-remove`) follow the same convention.

### 3.6 Request ids

Every response carries `X-Request-Id`. A caller may send its own (1 to 128 characters of `A-Za-z0-9._:-`) and it is echoed;
anything else is replaced by a fresh UUID. The same id is in every problem document (`request_id`), in the server logs and in
the audit log, so quote it when reporting a problem.

### 3.7 Rate limiting and throttling

What is enforced today:

- **Sign-in and recovery throttling.** Failed logins and re-authentications are counted per account and per client IP in a
  fixed window (15 minutes by default). After 5 failures for an account the answer is `429 account-locked`; after 30 failures
  from one IP, `429 too-many-requests`. Both send `Retry-After`. Password-reset requests and invitation lookups are throttled the
  same way.
- **Scan-resolve enumeration guard.** `GET /v1/scan/resolve` answers `429` after 60 lookups that match nothing within the
  window, per signed-in principal. The loaner scan flows (`POST /v1/loaner-pools/{id}/quick-checkout`,
  `POST /v1/loans/return`) count their unknown codes towards the same limit.
- The client address comes from `X-Forwarded-For` only when the operator sets `TRUST_PROXY` to the proxies in front of the API
  (default: nobody is trusted, so a forged header is ignored).

What is **not built yet**: the general per-tenant request limits by plan tier. The contract already describes the
`RateLimit-Limit`, `RateLimit-Remaining` and `RateLimit-Reset` response headers; they are not sent today (backlog M5-API-02).
Always honour `Retry-After` on any `429`.

## 4. Permissions model

  "signed in (browser session)" are self-service endpoints that need a cookie session, and "public" needs nothing.

| PUT    | `/v1/saved-views/{id}/sharing` | `view:share`                | If-Match | Share a view with the organisation, or stop sharing |

### Exports

CSV exports of lists, produced by a background job and downloaded through a short-lived link.

| POST   | `/v1/exports`      | `export:run` | -        | Export a list to CSV |
| GET    | `/v1/exports/{id}` | `export:run` | -        | Get an export        |
