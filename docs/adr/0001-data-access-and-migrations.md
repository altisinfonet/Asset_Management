# ADR 0001: Data access layer, migration tool, database roles and ids

Status: ACCEPTED (founder, 2026-11-18). Supersedes the earlier proposal of 2026-11-17 (Kysely), which the founder replaced with Prisma.
Date: 2026-11-17, revised 2026-11-18. Stories: M1-DB-01, M1-DB-02, M1-TEN-01..03.
Inputs: `docs/03_system_architecture.md` 5.3 and 8.5, `docs/validation/spike_rls_pgbouncer.md`, `docs/engineering/schema.sql`, `decisions.md` (ED-05, ED-08, ED-09).

## Context

Architecture 8.5 left two choices open: the query layer and the migration tool. Whatever is chosen must satisfy three requirements that come from the tenancy design:

1. **Per-transaction `set_config(..., true)`**: tenant context is set inside an explicit transaction, before any query, and vanishes at COMMIT/ROLLBACK.
2. **No session state behind PgBouncer** (transaction pooling, spike finding F3): no session-level `SET`, no `LISTEN`, no session advisory locks at runtime, named prepared statements only with `max_prepared_statements > 0`.
3. **SQL-first migrations that a reviewer can read**: RLS policies, partitions, triggers and grants are DDL that no ORM models well, and the schema lint must be able to judge the result.

The first proposal chose Kysely (a query builder) for requirement 3. The founder decided on 2026-11-18 to use **Prisma** as the query layer instead (typed models, relations and nested writes remove a lot of hand-written query code in the registry modules). Requirements 1 and 3 are not negotiable, so the decision below is Prisma used as a typed client only, on top of the existing SQL migrations.

## Decision

- **Query layer: Prisma Client 7.10.1 with the `@prisma/adapter-pg` driver adapter** (`prisma`, `@prisma/client` and `@prisma/adapter-pg` are pinned to exactly 7.10.1; the `latest` dist-tag on npm is a release candidate of 8.0.0 and must not be used). The adapter uses node-postgres, so it works through PgBouncer in transaction mode (verified by the isolation suite, see below). The generator is `prisma-client` (ESM, output `apps/api/src/generated/prisma`, gitignored, produced by `prisma generate` in `build`, `typecheck`, `test` and `test:e2e`). `prisma.config.ts` supplies the introspection URL (`MIGRATOR_DATABASE_URL`, direct, owner role).
- **Schema: SQL migrations stay the source of truth; Prisma never changes the database.** `prisma migrate` and `prisma db push` are never used. `apps/api/prisma/schema.prisma` is generated from a migrated database by `pnpm --filter @assettracker/api db:pull` (`scripts/db-pull.mjs`) and **committed**. **CI drift check**: migrate an empty database, run `db:pull`, `git diff --exit-code apps/api/prisma/schema.prisma` fails the job when the committed schema differs. The script is deterministic (it resets the file to a fixed header before introspecting and removes the five multi-column GIN index lines that Prisma introspects but then cannot validate, see Limitations).
- **Tenant isolation is unchanged in shape.** `withTenantTx(ctx, fn)` is `prisma.$transaction(async (tx) => { await tx.$executeRaw\`select set_config('app.tenant_id', ${tenantId}, true), set_config('app.actor_id', ...), set_config('app.request_id', ...)\`; return fn(tx) })`: an interactive transaction (default limits 5 s wait, 30 s run, overridable per call) whose first statement sets the transaction-local context. `withPreTenantTx(fn)`is the same transaction without a tenant, for the`identity`lookups and the control plane.`TenantRepository`exposes the transaction client only inside`withTenantTx` (AsyncLocalStorage) and throws outside it.
- **No query may run against tenant tables outside these helpers**, enforced three ways. (1) The only `PrismaClient` instance is private to `TenancyService`; a `Tx` cannot be obtained any other way. (2) ESLint (`apps/api/eslint.config.mjs`): only `src/tenancy` and `src/db` may import `@prisma/client`, `@prisma/adapter-pg`, `pg`, or the generated client (`**/generated/prisma/**`), type-only imports excepted; a unit test lints deliberate violations and fails if the rule stops firing. (3) A grep test fails the build on any session-level `SET app.` or `set_config(..., false)` in `src/` or `migrations/`.
- **Raw SQL is tagged templates only.** Partitioned tables (`audit_log`) and anything Prisma cannot model (expression filters such as `lower(email)`, `app.provision_tenant(...)`, `app.next_asset_tag(...)`, cross-schema joins without a foreign key) use `tx.$queryRaw` / `tx.$executeRaw` with tagged templates, so every value is a bound parameter. `$queryRawUnsafe` and `$executeRawUnsafe` are banned everywhere (including tests) by an ESLint `no-restricted-syntax` rule with a fixture test. `Prisma.raw()` (identifier splicing of a fixed, trusted name) is allowed only for static lists in tests.
- **Ids: UUIDv7 generated by the application** (`src/ids/uuidv7.ts`, RFC 9562 with a monotonic counter in `rand_a`), one code path for PostgreSQL 16, 17 and 18 (ED-08). Ids are passed explicitly on every create; there are no database-side id defaults and the lint rejects a `uuidv7()` default.
- **Errors**: database errors reach the app as `PrismaClientKnownRequestError` (`P2002`, `P2003`, `P2010`, ...) with the original node-postgres error under `meta.driverAdapterError.cause`. `sqlStateOf(err)` / `isUniqueViolation(err)` (`src/tenancy/errors.ts`) read the SQLSTATE through both shapes; code must never branch on Prisma codes alone.
- **Migrations: keep the custom runner**, SQL files `NNNN_name.sql` in `apps/api/migrations/`, applied by the `migrate` role as `app_owner` over a direct connection. After applying, `migrate` rolls the partition window forward (`app.ensure_partitions`), then runs `app.schema_lint()` and the role audit; a violation fails the run, which stops the deploy pipeline. The migration ledger is `public.schema_migrations` (schema-qualified because the owner's `search_path` leads with `app`). The runner, schema lint and maintenance code keep using `pg` directly (they live in `src/db`), because they need a session advisory lock and DDL.
- **Roles: `app_owner` and `app_user`** (the names in `schema.sql`, the schema lint and `data_model.md`). The backlog and the first compose file said `migrator` and `app`; those were renamed because (a) the lint and the accepted schema reference the `app_*` names, and (b) a role named `app` next to a schema named `app` makes the implicit `"$user"` search-path entry resolve to the schema, which is confusing and fragile. Both roles are created by `docker/postgres/init/01-roles.sql` (run once as a superuser: dev compose entrypoint, CI step, or by hand on a bring-your-own Postgres; idempotent). The script also sets the database owner, revokes `PUBLIC`, installs `pg_trgm` and `btree_gin`, and sets the roles' `search_path`. It deliberately does **not** use `ALTER DEFAULT PRIVILEGES`: defaults would cover new partitions, which must never be granted to `app_user`. Schemas, objects and every grant come from the migrations, which run as `app_owner`, so `app_user` owns nothing and has no `CREATE`.
- **Tenant-table conventions as SQL helpers** (migration 0002): `app.apply_tenant_conventions(table)` (ENABLE + FORCE RLS, the `tenant_isolation` policy in the `NULLIF` form on both `USING` and `WITH CHECK`, the `version`/`updated_at` trigger, DML grants on the table itself and never on a partition) and `app.create_tenant_table(name, body, ...)` (standard columns, `UNIQUE (tenant_id, id)`, tenant-led index, composite-FK-ready, then the conventions). Both are executable by `app_owner` only. A static test requires every `create table app.x` in a migration to be followed by `apply_tenant_conventions('app.x')`; the lint is the database-level guard.
- **Schema lint** (`app.schema_lint()`, migration 0008; CLI `schema:lint`, run by `migrate` and by CI): RLS enabled and forced with the NULLIF policy on both clauses, a tenant-led index, no grant on any partition, `security_invoker` views, no `SECURITY DEFINER`, no superuser/BYPASSRLS application role, `app_user` owns nothing and cannot create, no `uuidv7()` default, composite `(tenant_id, ...)` foreign keys between tenant tables, and a classification rule (every table is `tenant`, `non-tenant` with a `COMMENT ... 'non-tenant: <reason>'`, or a partition). Every rule has a failing fixture in `test/schema-lint.e2e.test.ts`.

## Deviations from `docs/engineering/schema.sql` (the accepted schema), all deliberate

1. Part A (roles, extensions) is the bootstrap script; Part B is split into migrations 0002 to 0008 and runs as `app_owner` without `SET ROLE`. `psql` meta-commands are gone.
2. RLS, policies, triggers and grants are applied per table by `apply_tenant_conventions` right after each `create table`, not by catalog loops at the end, so each migration is self-contained and the next wave's tables follow the same pattern.
3. M1 subset only. FKs that point at M2 tables are deferred and **must be added by the M2 migration that creates `app.location`**: `role_assignment.scope_location_id` and `asset.location_id` exist as plain nullable columns. `fill_default_company` is attached to `asset` only; M2 attaches it to location, person, accessory, consumable. `provision_tenant` omits `label_template` (M2 replaces the function).
4. `ensure_partitions` loops over every partitioned table in schema `app` instead of a hard-coded list, so `asset_history` (M2) is covered without redefining it.
5. `schema_lint` gains the composite-FK, classification and create-privilege rules (backlog M1-TEN-03), and the role rule covers any `app_*` role plus any role that can use the application schemas.
6. `identity.security_event` (control-plane security log, M1-TEN-08) and `identity` table comments are new.
7. The `pooling` profile of M1-REPO-03 is realised as: PgBouncer is **always on** in the dev stack (the API must use the production code path by default; the verification run needs it), and `docker compose --profile pooling run --rm pgbouncer-check` asserts transaction mode, `max_prepared_statements=100`, empty `server_reset_query`, pool size 4 and the `app_one` pool_size=1 alias.

## Controlled superuser path for backfills (M1-DB-02)

FORCE RLS binds `app_owner` too: with no tenant set it sees 0 rows, so an unscoped `UPDATE`/`DELETE` silently matches nothing. The normal procedure is therefore a per-tenant loop (worker job or script) that opens `withTenantTx` for each tenant, using the owner connection (`MIGRATOR_DATABASE_URL`) for a data fix that needs DDL-adjacent rights. Only when a cross-tenant operation is unavoidable (an emergency repair, a restore verification), a human runs it as the cluster superuser (`postgres`) from a one-off session outside the application: it bypasses RLS because superusers are exempt, so the run needs a written reason, a second reviewer on the SQL, a recorded start and end time, and a row count check per tenant afterwards. No application role is ever given BYPASSRLS, and the role audit (`schema:lint`, run in CI and by `migrate`) fails if any role that can use the `app` or `identity` schemas is a superuser or has BYPASSRLS.

## Consequences

- **Raw SQL stays for the database-specific parts**: partitioned `audit_log` writes, RLS-aware helper functions, expression predicates, and joins without a foreign key. They are tagged templates and covered by the isolation suite. Everything else (CRUD, relations, composite-key lookups) uses the generated client.
- **Prisma limitations accepted and worked around** (found while migrating wave 1):
  - _Introspection emits an invalid schema for multi-column GIN indexes_ (`(tenant_id uuid, name gin_trgm_ops)` via `btree_gin`): validation fails with "The Gin index field type Uuid has no default operator class", and `db pull` then refuses to run on its own output. `db-pull.mjs` resets the file first and drops those index lines; indexes do not affect the client and the migrations keep them.
  - _Columns filled by triggers are required on create_: `asset.company_id` is `NOT NULL` and filled by `fill_default_company`, but the generated create input requires it, so the caller looks up the default company. Same for any future trigger-filled column.
  - _Expression indexes/uniques_ (`lower(name)` unique constraints) and CHECK constraints are not modelled (the introspection warns); the database still enforces them and violations surface as `P2010`/`P2002` with the SQLSTATE under `meta`.
  - _Partitioned tables_ are introspected as ordinary tables (the composite primary key `(id, at)` is modelled), but the contract says writes go through raw SQL so partition routing and the "append-only, INSERT and SELECT only" grants stay visible in the code.
  - _Composite foreign keys_ `(tenant_id, x_id)` are modelled as relations with composite `fields`; creating through the unchecked scalar input (`tenant_id`, `category_id`, ...) works, nested relation writes would not set `tenant_id` and must not be used.
  - _`bytea`_ is `Uint8Array<ArrayBuffer>`; a Node `Buffer` needs `asBytes()` (`src/tenancy/bytes.ts`).
  - _Interactive transactions_ have a default 5 s limit and a 2 s wait: `withTenantTx` raises them (5 s wait, 30 s run) and exposes `TxOptions` for long jobs. PgBouncer still holds one server connection for the whole transaction, so keep transactions short.
  - _Errors_ are wrapped (`PrismaClientKnownRequestError`); `sqlStateOf` extracts the SQLSTATE.
- **A drift check is now part of CI** (migrate an empty DB, `db:pull`, `git diff --exit-code`); it replaces the follow-up "hand-maintained types" risk of the first proposal. Prisma Client generation adds a few seconds to `build`, `typecheck` and `test`.
- The custom runner has no down migrations and no diffing; expand/contract discipline (architecture 8.5) is the rollback story. The previous-release-schema upgrade check from M1-DB-01 is not automated yet: CI migrates an empty database twice (second run must be a no-op).
- Accepted exposure from ED-05 stays: `app_user` reads `identity` through the normal pool until the narrow `app_auth` role lands (before M4).
- Upgrading Prisma is a deliberate act: bump the three packages together, re-run `db:pull`, the full isolation suite direct and pooled, and read the release notes (Prisma 7 changed generators, config and the engine; 8.x is a release candidate at the time of writing).
