# ADR 0003: Module boundary lint and API conventions (platform kernel)

Status: PROPOSED (Claude, 2026-11-18); implements M1-PLAT-01 and M1-PLAT-02 and needs founder sign-off like every ADR.
Date: 2026-11-18. Stories: M1-PLAT-01, M1-PLAT-02.
Inputs: `docs/03_system_architecture.md` 4 ("Boundary rules", tool choice _proposed_), `docs/engineering/openapi.yaml` (Errors, Idempotency, Optimistic concurrency, Pagination), ADR 0001.

## 1. Boundary lint tool: ESLint `no-restricted-imports` (no new dependency)

**Decision.** The dependency-boundary lint required by M1-PLAT-01 is the ESLint config that already enforces the database-client rule of ADR 0001 (`apps/api/eslint.config.mjs`), extended with two rules. Each rule has a failing fixture in `src/tenancy/boundaries.test.ts`, which fails the build if the rule stops firing.

1. **Facade only.** A module is imported through `src/<module>/index.ts`; reaching into `../tenancy/tenant-tx.js` from another module fails lint. Modules with a facade today: `tenancy`, `platform`, `control-plane`, `identity`. A new module adds itself to `FACADE_MODULES`.
2. **Dependencies point downward.** Kernel directories (`platform`, `tenancy`, `control-plane`, `identity`, `config`, `logging`, `ids`, `db`, `context`) cannot import domain modules (`registry`, `lifecycle`, `tagging`, ... from architecture 4) or application entry points (`bootstrap`, `seed`, `cli`, `health`). Domain code may import kernel facades.
3. The database-client rule of ADR 0001 is unchanged: only `tenancy` and `db` may import `@prisma/client`, the adapter, `pg` or the generated client.

**Alternatives.** `dependency-cruiser` can express the same graph rules and draws the graph, but adds a dependency, a second config language and a second CI step for rules the existing ESLint setup already expresses with path patterns. `eslint-plugin-boundaries` needs element typing per file. Revisit dependency-cruiser if cycle detection or an architecture diagram generated from code becomes valuable (it is not needed to enforce the rules above).

**Limits.** Path patterns match import specifiers, so a deep relative path that happens to avoid `tenancy/` in its text (a symlink, a path alias) escapes the rule; the repo uses plain relative imports only. The rule does not detect table ownership (architecture 4 rule 1): that stays a review and RLS concern.

## 2. API conventions (M1-PLAT-02), where the contract left room

The contract is `openapi.yaml`; these are the choices the implementation had to make.

| Topic           | Choice                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Error documents | `application/problem+json`, members `type` (`<PROBLEM_TYPE_BASE>/<code>`), `title`, `status`, `code`, `detail`, `instance` (path), `request_id`, `errors[]` (`pointer`, `message`, `code`). Every failure is rendered by one global filter (`src/platform/problem.filter.ts`); unknown exceptions are a generic 500 with the request id, never the message or stack (they go to the log). Codes live in one catalog (`PROBLEM_CATALOG`): they are API surface and are never renamed.                                                                                                                                                                                                        |
| Validation      | `ZodValidationPipe(schema, source)`. A failing **body** is `422 validation`, a failing **query or path** parameter is `400 bad-request` (the contract's `BadRequest` text names "bad query parameter"); both carry `errors[]` with JSON pointers (`/items/0/qty`), `query:<name>` or `path:<name>`. zod `invalid_format` regex failures map to `code: pattern`.                                                                                                                                                                                                                                                                                                                             |
| Request id      | The incoming `X-Request-Id` is reused only when it is 1-128 characters of `A-Za-z0-9._:-` (an AWS `Root=1-...;` trace header is therefore replaced); otherwise a UUID is minted. It is echoed in `X-Request-Id`, in `request_id` of every problem, in the logs (Fastify request id), and it reaches `app.request_id` inside tenant transactions through an `AsyncLocalStorage` set in an `onRequest` hook (`src/context/request-context.ts`), so callers do not pass it by hand.                                                                                                                                                                                                            |
| Pagination      | `limit` 1-200 (default 50), opaque `cursor`, `include_total`, `sort`, `fields`. One helper (`listPage`) implements keyset pagination for any sort mix: fetch `limit + 1` rows, build `(a > x) OR (a = x AND b > y) OR ...` plus the unique `id` tiebreaker, `next_cursor` only when a further row exists. A cursor is `base64url(JSON {v, b, k})`; `b` is a hash of the sort and filters it was issued for, so reuse elsewhere is `400 invalid-cursor`. It is **not signed**: it carries sort-key values only, and tenant isolation does not depend on it (RLS). Nullable sort columns are not supported (cursor values cannot compare `NULL`); list specs must sort on `NOT NULL` columns. |
| ETag / If-Match | `W/"<version>"` from the trigger-maintained `version` column. `PATCH`/`DELETE`: missing `If-Match` is `428 precondition-required`, a stale one `412 precondition-failed` (the detail names the current tag), a malformed one `400`; `*` matches any existing resource; a list of tags is accepted. The write itself uses `UPDATE ... WHERE id = $1 AND version = $2`, so a race between the check and the write also ends in 412. `If-None-Match` on GET answers 304.                                                                                                                                                                                                                       |
| Idempotency-Key | See below.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Probes          | `GET /healthz` (liveness, no dependencies) and `GET /readyz` (database reachable **and** every migration shipped with the build is in `public.schema_migrations`; 503 otherwise) outside the `/v1` prefix; `/v1/health` stays for the existing contract and compose healthcheck. Migration `0009` grants `app_user` `SELECT (id)` on the ledger, nothing else.                                                                                                                                                                                                                                                                                                                              |

### Idempotency-Key design

The key row and the business write share **one transaction**:

1. A global interceptor, for `POST`/`PUT`/`PATCH`/`DELETE` with the header and an authenticated principal, opens `withTenantTx` for the request. The handler's own `withTenantTx` calls for the same tenant join it (nested calls already do), so no controller code changes.
2. It claims the key with `INSERT ... ON CONFLICT DO NOTHING` into `app.idempotency_key (tenant, principal, key)`. A concurrent duplicate **blocks on the unique index** until the first request commits or rolls back (`lock_timeout`, default 3 s, `IDEMPOTENCY_LOCK_TIMEOUT_MS`), then replays the stored response; if the first is still running after the wait, the duplicate gets `409 idempotency-key-in-flight` with `Retry-After`.
3. A key that exists with a different method, path, query or body (canonical JSON, sorted keys, sha-256) is `422 idempotency-key-reuse`.
4. A new key runs the handler and stores status, `ETag`/`Location` and the JSON body in the claimed row, committed together with the handler's writes. Replays set `Idempotent-Replayed: true` and do not run the handler.
5. A request that fails (any error) rolls back everything including the claim, so the retry executes again; this is the right behaviour for 5xx and costs nothing for 4xx. Expired rows (24 h) are replaced on the next claim; a purge job is M6.
6. `@IdempotencyRequired()` marks routes where a missing key is `400 idempotency-key-required` (check-out, check-in, transfer, import commit). Requests without a principal (login) ignore the header.

**Why in one transaction rather than a "reserve, run, complete" protocol.** A reserved-then-completed key needs a separate commit before the handler runs, so a crash between the two leaves a key stuck `in_flight` for 24 hours (a reaper or a timeout rule is then required), and "applied once" and "recorded once" can diverge. One transaction makes them atomic and removes the stuck state; the cost is that a duplicate waits on a lock instead of failing immediately, bounded by `lock_timeout`. The `state` column of the table is therefore only ever `completed` outside the claiming transaction.

**Limit.** Handlers must return JSON-serialisable values and set status/headers before returning; streams and file downloads are not idempotent-replayable (they are `GET`s, so out of scope).

## 3. Consequences

- Controllers declare behaviour instead of parsing headers: `@Principal()`, `@RequiredIfMatch()`, `ZodValidationPipe`, `listPage`, `@IdempotencyRequired()`. M1-REG, M1-AUTH and M2 build on these; the fixture controller in `test/support/demo-module.ts` shows the intended use on the `asset` table until the registry module exists.
- The auth guard (M1-AUTH) must set `request.principal = { tenantId, principalId }`; the kernel depends on that shape only.
- Bulk (`runBulk`, `src/platform/bulk.ts`): up to 100 items (configurable per endpoint), HTTP 200 with `results[]` (`index`, `status`, `data` or a problem document) and `summary`; items run in order; expected failures must be thrown as `ApiProblem` before writing, because under an Idempotency-Key the whole request is one transaction and a database error aborts it entirely. Exercised by the fixture route `POST /v1/demo/assets/bulk`; the first real bulk endpoint (M1-REG) may refine it.
- Rate-limit headers (`RateLimit-*`) are not implemented here (M5 per the contract's rate-limit section).
