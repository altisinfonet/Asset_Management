# ADR 0004: Platform services: audit, outbox, jobs, secret box, mail, observability

Status: PROPOSED (Claude, 2026-11-18); implements M1-PLAT-04..09 and M1-OPS-01 and needs founder sign-off like every ADR.
Date: 2026-11-18. Stories: M1-PLAT-04, M1-PLAT-05, M1-PLAT-06, M1-PLAT-07, M1-PLAT-08, M1-PLAT-09, M1-OPS-01.
Inputs: `docs/03_system_architecture.md` 5.2 (job tenant context, pg-boss rules), 7.3, 8, 9; `docs/validation/spike_rls_pgbouncer.md` (F5); ADR 0001 (roles, raw SQL), ADR 0003 (boundaries); `apps/api/src/ports/index.ts`.

## Context

Auth, registry and every later module need the same six capabilities: an audit trail written in the business transaction, domain events delivered reliably, background jobs with tenant context, secrets encrypted at rest, outbound mail, and operability (logs, metrics, traces). `src/ports/index.ts` fixed their interfaces so domain code can be written (and unit-tested with fakes) before the implementations existed. This ADR records how they are implemented and the choices the interfaces left open.

All implementations are bound in one place, `PortsModule` (`src/platform/ports.module.ts`, imported by `PlatformModule`, global): any module injects `AUDIT_WRITER`, `OUTBOX_PUBLISHER`, `JOB_QUEUE`, `MAIL_SENDER` or `SECRET_BOX` and never imports an implementation.

## 1. Mail: `MailSender.send` enqueues a job; the worker renders and sends (DECISION)

**Decision.** `send` never talks SMTP. Inside the caller's tenant transaction it (1) validates the template id, its data and the recipient, (2) inserts a row into `app.mail_outbox` holding the recipient and the template data **encrypted with the SecretBox** (context `<tenant_id>:mail:<mail_id>`), and (3) enqueues `mail.send` with `{ tenantId, mailId }` in the same transaction. The `mail.send` handler (worker role) opens the tenant transaction, locks the row, decrypts, renders the plain-text and HTML parts from the locale catalogue, sends over SMTP (nodemailer; Mailpit in dev), marks the row `sent` and **drops the stored message**. Failures retry with exponential backoff (6 retries, catalogue) and end in the dead-letter queue.

**Why.**

- The backlog says sending is "via a worker job, never inline in a request": an SMTP outage must not fail or slow a login or an invitation.
- Transactional: the mail exists if and only if the business change commits (an invitation that fails to save sends nothing; a committed one cannot lose its mail to a crash between commit and enqueue).
- The "ids only" rule for payloads (section 3) forbids the address and the reset/invitation link in `pgboss.*`, which has no RLS. The port's `MailMessage` carries both, so the message has to be stored somewhere RLS-protected; encrypting it at rest keeps a reset token out of backups and out of reach of anyone with a SQL console, and clearing it after delivery removes it from the system.
- One code path for every mail; the worker is the only role that needs SMTP credentials and network egress.

**Consequences.**

- `send` must run inside `withTenantTx` (it uses the ambient transaction) and throws otherwise. Mail that must go out before a tenant is known (a "your account was not found" notice) cannot use this path; M1-AUTH should not send such mail (it would also be an account-enumeration channel).
- Delivery is at-least-once (a crash between the SMTP acknowledgement and the commit re-sends on retry). Failed attempts are visible in the job queue / dead-letter queue, not on the mail row (the attempt runs in a transaction that rolls back).
- New templates: add a zod schema and a layout in `mail/templates.ts` and keys to the catalogue in `mail/i18n.ts`; a new language is a catalogue object, no template code changes. Only `en` ships in M1.

**Alternative rejected: send directly from `send`.** Simplest, but a request-path SMTP dependency, no retry, and "mail sent, transaction rolled back" is possible. **Alternative rejected: job payload carries the address and link.** Violates ids-only; leaks PII and tokens to every holder of the runtime role.

## 2. Audit (M1-PLAT-04)

- `PgAuditWriter.write(tx, entry)` is one `INSERT ... SELECT` on the partitioned parent `app.audit_log` through the caller's transaction (tagged `$executeRaw`, ADR 0001). Tenant id, actor id and request id are read **inside the statement** from the transaction GUCs `withTenantTx` sets, so a row can only describe the transaction's own tenant (RLS `WITH CHECK` is the second lock); callers cannot pass them.
- Actor type, client ip and user agent come from the request context (`src/context/request-context.ts`), set per HTTP request by `registerHttpObservability` and per job by the worker wrapper (`actorType: 'system'`, actor = the job id). `bindRequestIdentity()` (called by `RequestIdentityInterceptor` from `request.principal`, which the auth guard sets) fills tenant and actor mid-request. `RequestPrincipal` gained an optional `actorType` (`user` default, `api_key`, `integration`): the auth module should set it for API keys. `actor_user_id` is set only for `user`; other types use `actor_ref`.
- The diff is `{ before, after, meta }` JSON in the existing `diff` column (no migration). Everything is redacted by key (`password`, `secret`, `token`, `totp`, `otp`, `recovery`, `api key`, `private key`, `credential`, `authorization`, `cookie`, `signature`, ... any spelling, any depth; `audit/redact.ts`) **even when the caller already redacted**; `diffRecords(before, after)` produces the changed-fields-only diff.
- `app_user` has INSERT and SELECT on the parent only: UPDATE and DELETE fail with 42501 (tested). **Not in this change:** `GET /v1/audit-events` (M5-AUD-01, as agreed) and the route-registry lint "state-changing controller must call the audit writer" (needs the registry, M1-REG; the audit port makes it a one-liner then).
- **Retention-purge role design (required by the story).** Retention is per tenant but partitions are shared (architecture Appendix A, item 1), so dropping a partition cannot honour different tiers, and offboarding/DSAR deletion also need DELETE. Design for M4-DB-02: a dedicated login role `app_retention`, `NOLOGIN` by default in self-hosted and used only by a purge job that connects with its own credential; it has **DELETE and SELECT on `app.audit_log` only, no INSERT or UPDATE, and no BYPASSRLS**: it deletes inside `withTenantTx(tenantId)` so RLS still scopes every delete to one tenant, in bounded batches (`DELETE ... WHERE tenant_id = $1 AND at < $2 AND id IN (SELECT id ... LIMIT n)`). Partitions older than the longest retention tier are dropped whole by the owner role (`app_owner`, the migrator) in the monthly rotation. Each purge writes an audit row (`audit.purged`, count, cutoff) from a different role path (system actor). The role audit (`auditRoles`) is extended to allow exactly this role to hold DELETE on `audit_log`. The `app` role never gains DELETE. A hash chain (v3) must tolerate gaps created by purges.

## 3. Outbox (M1-PLAT-05) and the ids-only rule

- `PgOutboxPublisher.publish(tx, event)` inserts into `app.outbox_event` in the caller's transaction (tenant from the GUC). Migration `0020_outbox_relay` adds `next_attempt_at`, `last_error`, `dead_lettered_at` and replaces the pending index.
- `OutboxRelay` (worker role, poll every `OUTBOX_RELAY_INTERVAL_MS`, default 2 s) loops over the active tenants (control plane) and, **one event per transaction** under the tenant context: `SELECT ... WHERE pending AND next_attempt_at <= now() ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED`, runs the in-process subscribers **with the same transaction**, stamps `published_at`, commits. Any number of relays are safe (a claimed row is invisible to the others), and a subscriber's database writes commit atomically with the "delivered" mark: **exactly once for database effects, at-least-once for external ones** (make them idempotent on `event.id`).
- A failing subscriber rolls the transaction back (its own writes vanish); a second short transaction records `attempts + 1`, `last_error` and `next_attempt_at = now() + min(1 h, 2 s * 2^attempts)`; at `OUTBOX_MAX_ATTEMPTS` (default 8) the row is dead-lettered (`dead_lettered_at`) and skipped until an operator clears it. Events without subscribers are marked delivered.
- **Payload rule (ids only).** `pgboss.*` has no RLS (spike F5/section 5.3), so `app_user` can read every tenant's job payloads; outbox payloads are forwarded outside the system by webhooks (M5). Job and outbox payloads therefore carry ids, versions, counters, buckets and short codes only: UUIDs, numbers, booleans, null and `[A-Za-z0-9_.:-]{1,64}` strings, depth <= 3, <= 100 array items, <= 4 KB, identifier-like keys that do not name a secret or personal field. An email address, a URL, a name or a sentence cannot pass (`ids/ids-only.ts`; failing fixtures in `ids-only.test.ts`, enforced in `enqueue` and `publish`). Consumers resolve details from the ids under RLS.
- Scaling note: the relay polls per tenant; with thousands of tenants per cell, replace the poll with a per-tenant wake-up job enqueued in `publish` (same transaction) plus the periodic sweep. Not needed before M6.

## 4. Jobs on pg-boss 12.x (M1-PLAT-06/07)

- **Adapter.** `src/jobs` is the only code (with the owner-path provisioning in `src/db/provision-jobs.ts`) that imports `pg-boss` (ESLint, with fixtures). The `JOB_QUEUE` port is implemented by `PgBossJobQueue`.
- **Three instance kinds** (`jobs/boss-options.ts`, asserted in tests): *provisioning* (migrate step, direct connection, owner role; `createSchema` and `migrate` on), *runtime* (api, worker, scheduler; `app_user` through PgBouncer; `createSchema`, `migrate`, `supervise`, `schedule` all `false`), *maintenance* (one logical instance in the scheduler role; owner role, direct; `supervise` on). `useListenNotify` is `false` everywhere, no queue is created with `notify`, `JOBS_POLL_SECONDS` is validated to 1-2, and a test greps the sources for `notify: true`.
- **Provisioning** (`migrate` role, after the SQL migrations): pg-boss creates or upgrades schema `pgboss`; every queue of the **catalogue** (`jobs/catalogue.ts`: the one reviewable list of queues, with retry/backoff/expiry, priority class, runner and tenant scoping) is created with a `dead-letter` queue (created first) as `deadLetter`; then grants for `app_user` (USAGE on the schema, DML on tables and partitions, USAGE on sequences, EXECUTE on functions) **re-applied on every run**, plus `ALTER DEFAULT PRIVILEGES FOR ROLE <owner> IN SCHEMA pgboss` so objects created later by the owner (per-queue partitions, tables added by a pg-boss upgrade) are covered. The grants are then **verified** and a gap fails the deploy. The repository rule "no ALTER DEFAULT PRIVILEGES" (SQL migrations, tested) protects the partitions of tenant tables in schema `app`; it deliberately does not cover `pgboss`, which holds no tenant tables. Queues are created by `migrate`, never at runtime (no DDL for the runtime role); `enqueue` refuses an unknown queue.
- **Schema name (`JOBS_SCHEMA`, default `pgboss`).** Every instance kind, the provisioning step and the grant helpers take the schema from configuration (validated as a lower-case identifier). All roles of one deployment must agree. The e2e suite uses `pgboss_e2e` (set in `vitest.e2e.config.ts`, provisioned once by a vitest `globalSetup`), so a running compose `worker`/`scheduler` (default schema) cannot steal the tests' jobs and the suite needs no "stop the worker first" step. Chosen over a queue-name prefix because queue names are a reviewed catalogue that handlers, grants and the dead-letter wiring all key on; a schema keeps names unchanged and isolates queues, jobs, archive and pg-boss's own bookkeeping at once. CI has no worker, so it is unaffected.
- **Transactional enqueue.** `enqueue(name, payload, { tx })` sends through `db: { executeSql }` bound to the caller's Prisma transaction (`jobs/tx-db.ts`: `$n` placeholders are split and rebuilt as `Prisma.sql`, so values stay bound parameters and the banned `$queryRawUnsafe` is not needed). A rollback enqueues nothing (tested through PgBouncer). Inside a tenant transaction only that tenant's jobs can be enqueued.
- **Worker wrapper** (`jobs/worker.ts`). Handlers are registered with `registerTenant` (queue must be tenant-scoped in the catalogue; the handler receives a `tx`) or `registerSystem` (non-tenant queue; no transaction). A tenant job runs only after: `payload.tenantId` is a UUID (else `MissingTenantContextError`, nothing opened), the control plane knows the tenant (unknown: the job fails; suspended: skipped), then inside `withTenantTx({ tenantId, actorId: jobId, requestId: 'job:<id>' })`. Per-tenant fairness: the tenant id is the pg-boss **group** and `localGroupConcurrency` (`JOBS_TENANT_CONCURRENCY`, default 2) caps one tenant per process; priority classes interactive (20) > scheduled (10) > bulk (0) are set from the catalogue. Jobs are fetched in batches of 5 with burst-on-full-batch and settled one by one (`perJobResults`), so a backlog drains at handler speed and one failure never fails its batch mates (100 jobs across two tenants through PgBouncer drain in about 2 s, zero RLS violations).
- **Scheduler** (`jobs/scheduler.ts`). Producers enumerate the active tenants from the control plane and enqueue one job per tenant with `singletonKey = <producer>:<tenant>` and `singletonSeconds = <period>` (a unique index on queue/time slot/key): two schedulers, or a restart, cannot duplicate a job in a slot and nothing needs a lock (tested with three concurrent schedulers). pg-boss's own `schedule` feature is not used (`schedule: false` everywhere), so there is one cron mechanism we control and can test.
- **First jobs.** `tenant.heartbeat` (per-tenant no-op, proves scheduler -> queue -> worker -> tenant tx) and `maintenance.partition-rotate` (daily, `app.ensure_partitions`, executable by the owner only, so it is bound to the **scheduler** role, the only long-running role with the owner connection `MAINTENANCE_DATABASE_URL`).
- **Dead letters.** Exhausted jobs move to `dead-letter`; `JobAdmin.deadLetters()` lists them with source queue, tenant id, payload and failure text, served read-only on the **internal ops port** at `GET /admin/jobs/dead-letter`. A public `GET /v1/admin/...` needs the permission layer (M1-AUTH-01); until then nothing about queues is exposed on the public API port.
- **Roles as processes.** `api | worker | scheduler | migrate` in the one image. `worker`: pg-boss workers + outbox relay + ops server; `scheduler`: producers + maintenance instance + owner-only jobs + ops server. SIGTERM: stop fetching, finish running jobs, drain the relay, close the pools, flush traces, exit 0 (the role owns its signal handling; Nest `enableShutdownHooks` is not used in these two roles). Health: a heartbeat that pings the database every 10 s; `/healthz` is 200 while it is fresh, `/readyz` checks the database and the started queue runtime. Compose adds `worker` and `scheduler` services with healthchecks.

## 5. SecretBox (M1-PLAT-08)

- Envelope encryption: a fresh 256-bit data key per value, AES-256-GCM, wrapped by a `KeyProvider`. Ciphertext = `'SB' | format version | key id | wrapped data key | IV | ciphertext | tag`. The **encryption context** (`<tenant_id>:<purpose>`) is the payload AAD and is also bound into the key wrap, so a value copied to another tenant or purpose fails to decrypt (tested, plus tampering at every region of the envelope). The header (key id, wrapped key) is authenticated indirectly: altering it fails the unwrap.
- Rotation: `rewrap(ciphertext, context)` unwraps the data key with the key named in the header and wraps it with the current master key without touching the payload bytes (tested: the payload tail is byte-identical). Procedure: set the new key + `MASTER_KEY_ID`, keep the old as `MASTER_KEY_PREVIOUS` + `MASTER_KEY_PREVIOUS_ID`, re-wrap columns in batches (`needsRewrap`), then drop the previous key.
- `LocalKeyProvider`: keyring from `MASTER_KEY` / `MASTER_KEY_FILE` (Docker secret; base64 or hex, 32 bytes). Production refuses to start without one; elsewhere a throwaway key is generated with a loud warning (values do not survive a restart or cross roles: compose always provides the secret file). `KmsKeyProvider` is a stub that fails fast (M6-INF-05). `readSecret(NAME)` reads `NAME` or `NAME_FILE`. The logger redaction list covers `masterKey`, `dataKey`, `secret`, `token` ... (tested over every listed field at four nesting depths).

## 6. Observability (M1-OPS-01)

- **Logs.** pino JSON; a mixin adds `request_id`, `tenant_id`, `actor_id` from the ambient context (HTTP request, job, or the open tenant transaction); redaction of password, token, secret, key, TOTP, recovery, cookie, authorization fields at four depths.
- **Metrics.** prom-client on the **internal ops server** (`OPS_PORT`, default 9464, own `node:http` listener, not published by compose, not on the API port): RED per route pattern (`http_requests_total`, `http_request_duration_seconds`), `db_pool_connections{state}`, `jobs_queue_depth{queue,state}` (refreshed at most every 10 s on scrape), `jobs_processed_total`, `job_duration_seconds`, `outbox_events_total`, process/Node defaults. **`tenant_id` is never a label** (a test asserts it).
- **Tracing.** OpenTelemetry is off unless `OTEL_EXPORTER_OTLP_ENDPOINT` is set (then OTLP/HTTP through a `BatchSpanProcessor`). A server span per request and a span per job, `tenant_id` and `request_id` as attributes; pg-boss emits its own spans under the same global provider. Versions are pinned to the 2.x SDK line (`sdk-trace-node` 2.12, exporter 0.223): the newest exporter (0.301) requires the 3.x SDK that `sdk-trace-node` does not publish yet.
- **Not done:** the optional Sentry hook of the story (no consumer yet) and the OTel HTTP/pg auto-instrumentation (manual spans cover requests and jobs).

## 7. Port review (signatures unchanged)

All five ports were implemented as-is. Points the next author should know:

1. `JobQueue.enqueue` returns `Promise<string | null>`: a deduplicated enqueue (same singleton key in the same slot) has no job id and resolves to `null` (it used to be `''`, which is falsy too, so `if (id)` callers behave the same). Callers must treat `null` as "already queued".
2. `MailSender.send(message)` has no `tx` parameter; the implementation uses the ambient `withTenantTx` transaction (`currentTenantTx()`), which is what makes the mail transactional. It cannot send outside a tenant transaction (section 1).
3. `AuditEntry.meta` has no column of its own: it is stored as `diff.meta`.
4. `SecretBox.encrypt/decrypt` take a single `context` string; use `<tenant_id>:<purpose>` consistently (the mail module uses `<tenant_id>:mail:<mail_id>`).

## 8. Consequences for the threat model (M1-DOC-01)

- `pgboss.*` has no RLS: ids-only payloads are enforced in code, not by convention.
- The ops port is unauthenticated and read-only; it must stay off every public interface (compose does not publish it; the self-hosted reverse proxy must not route to it).
- The scheduler holds the owner credential at runtime (partition rotation, maintenance); the worker and api never do.
- `mail_outbox.message_enc` holds PII and tokens until delivery, encrypted under the master key; losing the master key makes undelivered mail unreadable (it will be retried into the dead-letter queue) and all other SecretBox values unrecoverable: the key is part of the backup set.
