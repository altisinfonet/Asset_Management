# ADR 0005: Asset registry: RLS-safe indexing, tag numbering, lists and bulk operations

Status: PROPOSED (Claude, 2026-11-18); implements M1-REG-01..11, the server side of M1-PLAT-03 and the route replay of M1-TEN-04. Needs founder sign-off like every ADR.
Date: 2026-11-18. Stories: M1-REG-01..11, M1-PLAT-03, M1-TEN-04.
Inputs: `docs/engineering/openapi.yaml`, `docs/engineering/data_model.md`, ADR 0001 (raw SQL), ADR 0003 (conventions), ADR 0004 (ports); `apps/api/test/perf/registry-perf.e2e.test.ts` (the measurements quoted below).

## 1. Row-level security makes `lower()`, `ILIKE`, `@@` and `@>` unindexable

**Finding.** `app_user` is subject to RLS (`tenant_id = (select nullif(current_setting('app.tenant_id', true), '')::uuid)`). PostgreSQL only turns a user predicate into an **index condition** when every function in it is `LEAKPROOF` (otherwise it could leak rows the policy hides, through error messages). On PostgreSQL 18: `texteq`, `uuid_eq`, `date_ge/le`, `timestamptz_ge` and `text_lt/ge` are leakproof; `lower(text)`, `texticlike` (`ILIKE`), `ts_match_vq` (`@@`), `jsonb_contains` (`@>`) and `similarity_op` are not. Measured with `EXPLAIN` on 50,000 rows: `WHERE lower(asset_tag) = 'x'` ignored the unique expression index `(tenant_id, lower(asset_tag))` and scanned the whole tenant (22 ms at 50k, linear in tenant size); after `ALTER FUNCTION lower(text) LEAKPROOF` (superuser, rolled back) the same query used the index in 0.1 ms. The trigram, full-text and jsonb GIN indexes of migration 0005 are used only for their `tenant_id` (btree_gin) column, never for the search operator.

**Decision.** (a) Exact lookups use **stored lower-case key columns** (`asset_tag_key`, `serial_key`, generated `always as (lower(...)) stored`, migration 0030) compared with `=`: a plain btree, leakproof, O(log n). The tag uniqueness index (ED-12) and the serial index now sit on those columns. (b) Substring search (`q`, `GET /v1/search`) is `strpos(search_text, lower($q)) > 0` over one stored column that joins tag, serial and name with `chr(31)`: a **tenant-bounded scan** (the index bounds it to the tenant's rows; one cheap predicate per row instead of three `ILIKE`s). (c) Custom field filters use `custom_data @> ...` as a filter on the tenant's rows. (d) The status label is not joined into the list query (a join let the planner start from the 7-row label table); names are attached to the returned page afterwards.

**Consequences.** Exact tag / serial lookups and `scan/resolve` stay index lookups at any size. `q`, `cf[...]` filters and search scale linearly with the **tenant's** asset count (measured at 50,000 assets with another 50,000-asset tenant present: list p95 11-36 ms, search p95 <= 51 ms, see section 6). The GIN and trigram indexes of 0005 are dead weight for these predicates and stay only for a future where the functions are leakproof or the search moves out of Postgres; revisit when a tenant exceeds ~500k assets. Mitigations if needed, in order: a leakproof wrapper installed by the bootstrap superuser (not available on managed databases), a prefix index (btree range on the key columns), a dedicated search engine behind the same `/v1/search` contract (M4+). Full-text search of `notes` was dropped: the contract specifies tag, serial and name, and a per-row `to_tsvector` costs more than the budget allows without an index it cannot use.

## 2. Asset tag numbering (M1-REG-06, ED-12)

The template (`prefix`, counter `width`, `use_category_prefix`) lives in `app.tenant.settings.asset_tag_template` and is edited with `GET/PUT /v1/settings/asset-tag-template` (`catalog:read` / `catalog:manage`, `If-Match` = tenant version). The tag is `prefix + category tag_prefix + zero-padded counter`; the counter row is `(tenant_id, full prefix)` in `app.asset_tag_counter`, bumped by `INSERT .. ON CONFLICT DO UPDATE .. RETURNING`, which holds a row lock until the transaction ends: concurrent creates in one tenant serialise on it and get distinct numbers, other tenants and other prefixes never wait. Counter rows roll back with the transaction, so a tag that was never stored is never skipped; a stored tag is never issued again (the unique index covers archived assets). A manually entered tag overrides the template and consumes no number; a generated tag that collides with a manual one is skipped. **A tag cannot be changed after creation** (`PATCH` with another `asset_tag` is 422 `immutable`): renaming would free the old tag and violate ED-12; re-tagging means creating a new asset. Tested with 100 parallel creates in one tenant (100 distinct tags) and two tenants allocating independently.

## 3. List, filters, pagination (M1-REG-07)

`GET /v1/assets` is one raw SQL statement assembled from bound fragments (`asset-queries.ts`); every sort key comes from a fixed table, never from user text. The keyset cursor is built on the platform primitives (`parseSort`, `bindingFor`, `encodeCursor`) but compares **text forms with full precision** (`to_char(created_at, ...US)` cast back to `timestamptz`): the platform's Prisma-based `listPage` reads a `Date`, which truncates PostgreSQL's microseconds, and rows created in one transaction (seed, import, bulk) share a timestamp, so a millisecond cursor skips or repeats rows. The unique tiebreaker `id` follows the direction of the first sort key (newest first stays newest first). Nullable sort columns (`name`, `purchase_date`, `warranty_end`) sort NULL smallest through `coalesce`. A forged cursor with the right binding but an uncastable value is `400 invalid-cursor`. `GET /v1/assets?tag=` / `?serial=` are the exact fast path. Filters the contract lists but that need M2 tables (`assigned`, `assigned_person_id`, `loaner_pool_id`, `include_sublocations`) are `400` until M2; `location_id` is accepted as a filter, but a non-null `location_id` on a write is 422 until the location table exists. The catalog lists (categories, models, ...) use the platform `listPage`; its millisecond cursor limitation applies to their `created_at` sort (tables of hundreds of rows, default sort `name`), noted for M2.

## 4. Writes, clone and bulk (M1-REG-05, -09)

Every write is one tenant transaction containing the change, the audit row and the outbox event (`AUDIT_WRITER`, `OUTBOX_PUBLISHER`), guarded by `UPDATE .. WHERE id AND version` (a lost race is 412). References (category, model, status, vendor, parent, company) and custom data are validated **before** the row is touched and reported together as field-level `errors[]`. Custom values are coerced to canonical JSON (`"16"` -> 16); unknown keys are rejected; `null` removes a key; a required field must end up with a value; a category change re-validates the whole object. Archived definitions keep their stored values readable. A delete or type change that would orphan data is `409` with an RFC 9457 extension member `usage` (counts); a custom field's type or category cannot change while assets hold values.

Clone (`POST /v1/assets/{id}/clone`) is all-or-nothing. Bulk (`POST /v1/assets/bulk-update|bulk-archive|bulk-restore`, up to 100 ids, `Idempotency-Key` supported) uses the platform `runBulk` and runs **each item in a savepoint**, so a failing item (not found, archived, stale, validation, unique violation) is rolled back and reported alone and the others commit; each item writes its own audit row and outbox event, and one `bulk_operation` audit row plus a `bulk_operation.completed` event describe the request. These endpoints, the tag template and `invalid-cursor` were added to `openapi.yaml`; they are not in the first contract draft.

## 5. Contract and isolation guardrails (M1-PLAT-03, M1-TEN-04)

`docs/engineering/openapi.yaml` is bundled to `apps/api/openapi.generated.json` by `scripts/bundle-openapi.mjs` (called by `ensure-generated.mjs` before build, typecheck and tests, and part of the Docker build) and served at `GET /v1/openapi.json` (public, ETag). `route-rules.test.ts` fails when an implemented route differs from the contract in path, method, permission or success status, when a registry operation is missing, or when an API problem code is not in the catalogue; `contract.e2e.test.ts` calls every registry operation and validates status, body and problem documents against the schemas; every e2e client request is recorded and checked against the documented statuses. `route-replay.e2e.test.ts` replays every route as tenant B with tenant A's ids and fails when a route has neither a replay case nor a reasoned exemption.

## 6. Measured on the real stack (50,000 assets in each of two tenants, `app.inject`, server side)

| Operation | p50 | p95 | Budget |
|---|---|---|---|
| list, default page of 50 | 9 ms | 11 ms | 500 ms |
| list, deep cursor / limit 200 / filters / sorts | 8-15 ms | 13-36 ms | 500 ms |
| `?tag=` / `?serial=` exact lookup | 6 ms | 7-9 ms | 150 ms |
| `scan/resolve` | 7 ms | 9 ms | 150 ms |
| search (exact, partial, word, 2 characters) | 22-42 ms | 37-51 ms | 200 ms |
| mixed load, 8 concurrent clients | 34 ms | 60 ms | 500 ms |

The suite asserts the budgets and that the hot statements use index plans (`asset_created_idx`, `asset_tag_uq`, `asset_serial_idx`; `q` is bounded by the tenant index, never a table scan). `PERF_ASSETS` overrides the size, `test-results/registry-perf.json` and `registry-plans.txt` are the artifacts for the nightly job (M1-CI-05).
