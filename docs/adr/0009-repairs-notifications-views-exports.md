# ADR 0009: Repairs, notifications, saved views and CSV export (M2 wave 2)

Status: PROPOSED (Claude, 2026-11-19); implements M2-MNT-01, M2-NOT-01, M2-REG-01, M2-REG-02 and M2-AUTH-01 (API side) and needs founder sign-off like every ADR.
Date: 2026-11-19. Stories: M2-MNT-01, M2-NOT-01, M2-REG-01, M2-REG-02, M2-AUTH-01 (and the isolation part of M2-SEC-01 for the new tables).
Inputs: ADR 0004 (ports, outbox, jobs, mail inside a tenant transaction), ADR 0005 (RLS-safe indexing), ADR 0006 (files), `docs/engineering/decisions.md` ED-13/ED-15 (custody, asset state machine), `docs/05_backlog.md` (E2.6, E2.9). Contract: the `[M2-W2 NOT]` block of `docs/engineering/tools/gen.mjs`. Migrations 0090-0094.

## Context

Four features land together and share infrastructure: a repair log that changes what an asset may do, a notification module that every later story (loans, imports, low stock, labels) plugs into, per-user saved list views, and CSV export of lists. Each had open design choices the backlog does not settle: how a repair interacts with custody and status, how a domain event becomes a notification without the producer knowing, how not to send fifty emails, who may see an export file, and what "shared view" means for permissions.

## 1. Repairs: status moves are remembered, one open record moves an asset (DECISION)

`app.maintenance_record` (table of schema.sql B10, plus `set_status_id`). Opening a record may move the asset to a status (`set_status_id`, an `undeployable` label as a rule; `deployable`, `pending` and `undeployable` are allowed, never `deployed`, `lost` or `archived`). The status the asset had is stored as `restore_status_id` (the tenant's default deployable status when the asset was checked out), and put back by `complete` or by cancelling, **only while the asset still has the status the repair gave it** (a status somebody chose meanwhile is never overridden; an explicit `restore_status_id` on the completion request wins and is always applied). The backstop is a partial unique index: **one open record per asset may move its status**; a second one is `409`, a note-only record (no `set_status_id`) is always allowed. That is what makes "restore the previous status" unambiguous.

Check-out is blocked by the existing state machine (`asset-not-deployable`: only `deployable` assets leave), so the in-repair status needs no new rule. `open_repair` joins the asset action table (`registry/asset-actions.ts`: refused for archived, lost and retired assets, and for a checked-out asset), is offered by `scan/resolve` (`allowed_actions`) when the caller holds `repair:manage`, and the state-machine test grew a column.

A checked-out asset goes to repair through check-in first, or with `force_checkin` + `force_note` (+ `set_status_id`, so it cannot be handed out meanwhile): the repair service calls `CustodyService.checkin` in the same transaction (joined, ADR 0004), so the custody period is closed with the note, the check-in history and audit are written as usual, then the repair opens. The caller needs `asset:checkin` on top of `repair:manage` (checked in the service; the contract has one `x-permission` per operation, and no new permission was worth a role migration). Archiving or disposing of an asset with an open repair is `409` (the contract already promised it for archive).

Money is `{amount_minor, currency}` in `cost_minor` + `currency`; totals per asset (`GET /v1/assets/{id}/repair-summary`) are one entry per currency, never converted. History events use the existing `repair_opened` and `repair_completed` types (cancelling is `repair_completed` with `outcome: cancelled`: the type list is a database CHECK). Photos and invoices are attachments with owner `maintenance_record`; `attachment_ids` link photos uploaded against the asset beforehand, exactly like check-in photos.

## 2. Notifications: a port, a table of subscriptions, rows plus mail in one transaction (DECISION)

**`NOTIFIER` port** (`src/ports`, fake in `fakes.ts`): `notify(tx, {type, recipients, vars, entity, link, dedupeKey})`. The implementation (`notifications/notification.service.ts`) runs in the caller's tenant transaction, like `MAIL_SENDER`: for each recipient it applies the tenant rule (a type switched off notifies nobody) and the user's preference, inserts the notification (unique `(tenant, user, dedupe_key)`: an outbox redelivery or a producer that fires twice is a no-op), and either queues the mail through `MAIL_SENDER` (itself a row plus a job in the same transaction), defers it to the digest, or skips it. Every decision is a row of `notification_delivery` (the log administrators read: `delivered`, `queued`, `deferred`, `skipped`; `queued` means "handed to the mail queue", whose own retries and dead-letter list apply).

**Types are code, not rows** (`notifications/types.ts`): label, description, default delivery, who gets it, whether an administrator may re-address it. Texts are an English message catalogue per type (`templates.ts`: `notification.<type>.title|body`), and the same title and body are the in-app text and the email (one generic mail template `notification.message`, so the mail module knows nothing about notification types). Preferences are per user and type (`in_app`, email `immediate | digest | off`); rules are per tenant and type (`enabled`, optional `recipient_roles` for types addressed to "users who hold a permission").

**Subscriber registry = one table.** `notifications/subscriptions.ts` maps an outbox event type to a notification type, a recipient resolver and a `describe` function (template variables, link, subject; it loads names under RLS because outbox payloads are ids only). The `NotificationSubscribers` provider subscribes every entry to the outbox relay at boot; the relay (worker role) runs entries inside its tenant transaction, so reading the subject, creating the notifications and marking the event delivered are one atomic step and a failure retries then dead-letters (ADR 0004). A module that wants notifications adds a type, a text and ONE entry; nothing else changes. Wired on main today: `attachment.infected` (to the uploader), `asset.checked_out` (to the assignee when they have a login), `export.completed`. Wired best-effort for the parallel stories: `consumable.low_stock` (to holders of `consumable:manage`) and `label.batch.ready` (to `requestedBy` / `createdBy` in the payload); the integrator must check those two payloads. Types and texts exist for `loan.overdue`, `loan.due_soon` and `import.completed`; their entries come with their producers (M2-LOAN-03, M2-IMP).

**Throttling and digest.** More than 10 immediate emails to one user within an hour are folded into the digest (`reason = throttled`). The digest job `notification.digest` (daily per tenant, scheduler producer, worker handler) sends ONE mail per user listing at most 50 items ("and N more"), marks them `digested` and logs it. A burst of 50 events is 10 mails plus one digest, never 50.

Not built: notification retention (rows are never deleted yet; the runtime role has no `DELETE` on `notification`), web push, per-channel templates beyond English, quiet hours.

## 3. Saved views: server-side, opaque to the server, sharing is its own permission (DECISION)

`app.saved_view` per user and list (`resource = assets` for now): `filters` (JSON object, <= 12 KB), `columns` (<= 40), `sort`, `is_shared`. The server does not interpret the filters except to **warn**: ids under `status_id`, `category_id`, `location_id`, `model_id`, `vendor_id`, `manufacturer_id`, `person_id`, `assigned_person_id` that no longer resolve (`not-found`) or are archived come back as `warnings[]` on every read, so the client applies the rest of the view and says what was dropped (M2-REG-01). Names are unique per user and list and among shared views, compared through a stored generated `name_key` (ADR 0005); at most 50 views per user and list.

Own views are **self-service** (a signed-in browser session, no permission: a view is not a tenant resource); **sharing is a separate operation** (`PUT /v1/saved-views/{id}/sharing`, `view:share`) rather than a field of create/update, because the contract allows one permission per operation and a field-dependent permission would be invisible to the role matrix. Only the owner edits, shares, unshares or deletes (anybody else gets `404`, also for shared views; others read a shared view and copy it). `view:share` is granted to the Administrator (`*`) and the Asset manager; so is `export:run`; `notification:manage` (rules, delivery log) belongs to the Administrator only. Migration 0094 updates existing tenants and replaces `app.provision_tenant` starting from the 0011 definition (only the asset-manager array changed).

## 4. CSV export: a job, a short-lived link, formula-safe cells (DECISION)

`POST /v1/exports` (`export:run`, plus the read permission of the list) stores a request (`app.export_job`) and queues `export.run` (ids only) in one transaction; the worker reads the list **through the same services the list endpoints use** (`AssetsFacade.list`, `PeopleService.list`, `LocationsService.list`, 200 rows per page, keyset cursors, running as the requester so RLS and filters behave identically), builds a UTF-8 CSV with a byte order mark and CRLF, writes it with `StorageAdapter.write` under `tenants/<tenant>/<yyyy>/<uuid>.csv`, and publishes `export.completed`. The StorageAdapter port has no streaming write, so the file is assembled in memory: **at most 100,000 rows** (a longer list fails the export with a sentence). Filters are validated like the list query when the export is requested (a bad one is `422` now, not a failed job later) and again when it runs (a custom field deleted meanwhile fails the export with a sentence and no retry; an unexpected error is retried twice and then recorded as failed).

An export belongs to its requester (`404` for everybody else, also administrators and other tenants). `GET /v1/exports/{id}` issues a presigned download (default 120 s, `FILES_DOWNLOAD_URL_TTL_SECONDS`); **requesting, completing and every issued link are audited** (`export.requested|completed|failed|downloaded`, `sensitive_read: true`, M2-REG-02's "audited as a sensitive read"). Files are deleted 24 hours after completion by `export.sweep` (hourly per tenant); an expired export reports `expired` immediately. At most five exports per user may wait.

**Formula injection.** A text cell starting with `=`, `+`, `-`, `@`, a tab or a carriage return gets a leading apostrophe (`guardFormula`); numbers are written as numbers and never prefixed. The inverse, `stripFormulaGuard`, removes exactly that apostrophe and is exported for the importer, so the round trip to the importer (M2-IMP) returns the original values; the importer story must call it on text cells. Asset columns follow the list (`asset_tag, name, serial, category, model, status, location, assigned_to, ...`) with names instead of ids plus one `cf:<key>` column per active custom field; the importer maps by those headers.

## 5. MFA policy in `/auth/me` (DECISION)

`mfa_policy: { required, scope }` joins `Me` (M2-AUTH-01): `scope` is the tenant setting `off | admins | all`; `required` is exactly what `DELETE /v1/auth/mfa` enforces (`mfaRequired(policy, permissions)`: `all`, or `admins` for roles holding `*` or `user:manage`) and is always `false` for an API key. The Security page can therefore hide "Turn off" instead of explaining the policy after a `403 mfa-required-by-policy`.

## Consequences

- New contract (`[M2-W2 NOT]`): 19 operations (tags Repairs additions, Notifications, Views, Exports), `Me.mfa_policy`, new schemas; permissions `export:run`, `notification:manage`, `view:share`; no new problem codes.
- New tables: `maintenance_record`, `notification`, `notification_preference`, `notification_rule`, `notification_delivery`, `saved_view`, `export_job`, all with the tenant conventions, composite foreign keys and isolation tests (`test/isolation/wave2-isolation.e2e.test.ts`) and route-replay cases for every new route.
- New queues: `notification.digest` (daily), `export.run`, `export.sweep` (hourly). `JobHandlerRegistry` registers the handlers in the owning modules.
- Open for the integrator: the two best-effort subscriptions (`consumable.low_stock`, `label.batch.ready`); the importer must strip the formula guard; the accessory/loaner assignment keys (wave 1 notes) are unrelated to this wave.
- Web (not in this change): bell with unread count and list (`/v1/notifications*`), preferences screen, admin rules and delivery log, repairs tab and "open repairs" list, saved-view picker on the asset list (the web keeps views in `localStorage` today), export button with polling, and hiding "Turn off" from `Me.mfa_policy.required`.
