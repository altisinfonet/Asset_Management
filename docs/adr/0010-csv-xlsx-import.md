# ADR 0010: CSV / XLSX import with a mandatory dry run (M2 wave 3)

Status: PROPOSED (Claude, 2026-11-24); implements M2-IMP-01..07 (the backend of the import wizard, M2-IMP-08, and the corpus and real-data trial, M2-IMP-09, are other stories) and the import part of M2-OPS-01; needs founder sign-off like every ADR.
Date: 2026-11-24. Stories: M2-IMP-01, M2-IMP-02, M2-IMP-03, M2-IMP-04, M2-IMP-05, M2-IMP-06, M2-IMP-07.
Inputs: `docs/03_system_architecture.md` (5.2 jobs, 6.b import flow), ADR 0004 (ports, jobs, outbox), ADR 0005 (RLS-safe indexing), ADR 0006 (files, scanning), ADR 0009 (exports and the formula guard), `docs/engineering/decisions.md` ED-18 and ED-19. Migration 0110. Contract: the `[M2-W3 IMP]` block of `docs/engineering/tools/gen.mjs`.

## Context

Import is the feature that decides whether a first customer ever sees value ("100 labelled assets in 30 minutes"). Four things must hold at once: a dry run changes nothing and says exactly what a commit would do; the commit goes through the same code as the API, so no rule, audit row or event is bypassed; a file of 100,000 rows neither fills the worker's memory nor holds a database transaction for minutes; and a crash at any moment leaves the data and the job in a state that can be resumed without duplicates. The first drafts of the contract (`ImportJob`, five states, `match_on` options) predate all of that and are replaced (ED-18).

## 1. The pipeline: one file, one pass, rows stored (DECISION)

`POST /v1/imports` creates a `draft`. The file is an ordinary attachment (`entity_type: import_job`, `kind: import_file`), so it goes through the whole upload pipeline of ADR 0006 (type sniffing, size caps, ClamAV) before anything parses it; `POST /v1/imports/{id}/analyze` queues `import.analyze`, which waits (re-queues itself every 5 s, 15 min at most) while the scan is pending and refuses an infected or rejected file. The worker reads the object **as a stream, once**: detects format, encoding, delimiter and header row, profiles every column, keeps 50 sample rows and writes **every data row into `app.import_row`** (as the array of its cells), 1,000 rows per insert. Everything later (mapping edits, dry run, commit, the error report) works from the rows in the database and never parses the file again: changing the mapping costs nothing, and a 100,000-row dry run is not bounded by the speed of the parser. The price is storage (about 30 MB for 100,000 rows of 15 cells) and that the rows hold tenant data (ED-19).

Caps: `IMPORT_MAX_ROWS` (default 100,000) data rows per file, `IMPORT_MAX_CONCURRENT` (default 2) running imports per tenant (`429 import-quota-exceeded`), the attachment cap of the tier for the file itself, 500 columns and 32,000 characters per cell.

## 2. Parsing: our own CSV reader, `yauzl` + `saxes` for XLSX (DECISION)

**CSV** (`importer/csv-reader.ts`, no dependency): a 100-line incremental state machine (RFC 4180 plus the usual leniencies) over decoded text chunks. Encoding: a byte order mark, or UTF-16 without one (NUL in every second byte), wins; otherwise UTF-8 when **every** byte sequence of the whole file is valid UTF-8 (one streaming pass with a fatal `TextDecoder`), else Windows-1252, the code page of "CSV" saved by Excel on Windows; a NUL byte in anything else is "not text". Delimiter: `, ; TAB |`, chosen by how consistently each splits the first 25 lines outside quotes. Errors carry the line the record starts on ("Line 3: a quoted field is never closed", "text after the closing quote"), never a stack trace. The upload sniffer of ADR 0006 section 3 accepted only NUL-free UTF-8 as CSV; for **`import_file`** attachments it now also accepts UTF-16 (with a BOM) and Windows-1252 text (decoded for the markup check only), nothing else changes.

**XLSX** (`importer/xlsx-reader.ts`): `yauzl` (random-access zip reader, maintained; v3 released 2026-06) and `saxes` (the SAX parser behind jsdom; stable). The sheet XML is parsed as a stream, one cell at a time. An XLSX cannot be decoded in a single pass because Excel writes `sharedStrings.xml` **after** the sheets, so the object-store stream is spooled to a **temporary file** (never into memory, deleted afterwards), the zip's central directory gives random access, and memory is bounded by the shared-string table (capped at 64 M characters) plus one chunk of XML. Typed dates are recognised by the cell's style (built-in and custom number formats) and returned as ISO text; booleans, inline strings, `_x000D_` escapes, sparse cells, hidden sheets and the 1904 date system are handled. Zip bombs: caps on entries, per-part sizes and the inflated size of the sheet. Rejected libraries: `xlsx` (SheetJS; the npm package is unmaintained and carries known CVEs), `exceljs` (last release 2024-12, large tree, its streaming reader needs the shared strings first), `read-excel-file` (loads the sheet into memory). `fflate` (maintained, no dependencies) writes the template workbooks. Legacy `.xls` is refused with a sentence.

Header detection: the row the user named (`parse.header_line`), else the first row of the first 40 with at least half as many filled cells as the widest of the first ten and mostly non-numeric text (a title line above the table has one cell). Blank and repeated headers are named (`Column C`, `Serial (2)`).

## 3. Mapping, values and references (DECISION)

A **mapping** assigns each column index to a target field of the entity (`FIELD_SPECS`, which is also the data dictionary of the templates), to `cf:<custom field key>` (assets) or to nothing; the heuristic suggestion is case- and punctuation-insensitive over a synonym table ("Serial No", "S/N", "Service Tag") and fills the mapping at analysis. `mapping.constants` gives a target a text without a column (the Google preset's `category: Chromebook`). **Options** (`match_on`, `on_match: skip | update | error`, `blank_cells`, `date_format`, `number_format`, `default_currency`, `references`, `defaults`, `assign`, `detect_changes`) and the **value map** (per reference kind, per normalised source value: an id, "create it" or "treat as empty") are stored on the job. A saved **template** is a mapping by header text plus options, per tenant.

Reference columns (category, manufacturer, model, status, location, department, vendor, person) resolve in this order: value map entry, exact name match ignoring case and padding, then the policy of the kind: `create` (default for everything except status and person) or `must_exist`. Locations are paths (`Site > Building > Room`, separators `> / \ |`), found by walking the tree level by level, a bare name only when exactly one location has it; missing parents are created. A status label is never created (it needs a state type); a person is created from an email or a name only when the policy says so. Dates: ISO, month names and unambiguous day/month are read; `03/04/2024` needs `dmy` or `mdy` unless the column proves its order (a `25/04` somewhere), which the analysis writes into the mapping. Numbers follow `number_format` (`auto` reads `1.234,50` and `1,234.50`; `1,234` is a thousand); money becomes minor units with the currency of the row, its symbol, the job default or the tenant base currency.

## 4. Dry run: the same validators, no writes (DECISION)

The dry run is a sequence of worker steps (section 6) over the stored rows. Per batch: map the cells; compute the match keys; find duplicates **inside the file** (a stored key per row and one indexed lookup per batch: the first row wins, later ones follow `on_match`) and **against the registry** (one lookup of tags, serials and external ids per batch); resolve references (announcing, not creating, what is missing: `will-create` warnings, summarised on the job); then validate.

- **Assets** call `AssetsFacade.createInTx` / `updateInTx` with `dryRun: true`: the code that runs every check of `POST /v1/assets` and `PATCH /v1/assets/{id}` (category, model, status, location, department, vendor, custom fields, tag and external-id uniqueness, immutable tag) and returns before the first write. An update additionally reports `changed`, so a row that would change nothing is `skip` ("unchanged"), which makes a re-import of the same file a no-op.
- **People, locations and departments** (a few thousand rows at most) call the service of the API inside a savepoint that is **always rolled back** (`probe`), so their validation, uniqueness rules, triggers and constraints are the real ones, and audit rows and events written on the way vanish with the savepoint.
- A row whose references are announced but not yet there (a new category) skips the checks that need the id and says so (`validated-at-commit`); the commit repeats everything.

The invariant "a dry run touches no registry data" is tested: row counts of every registry table, and of audit rows and events other than the import job's and its attachment's, are equal before and after. The result is a verdict per row (`create`, `update`, `skip`, `error`, with `errors[]` and `warnings[]` carrying a target field and a message), the counts, `errors_by_code`, `will_create`, and a **digest**: SHA-256 over the file's checksum, parse settings, mapping, options, value map, counts and an MD5 over every row's plan. `commit` must quote it; any edit of mapping, options or value map clears it (`409 import-stale-dry-run` / `import-wrong-state`).

## 5. Commit: batches, ETags, before-images (DECISION)

Each step writes its rows through `AssetsFacade`, `PeopleService`, `LocationsService`, `DepartmentsService` and the catalogue services (the import passes `{ import_job_id, import_row }` as audit metadata, asset history carries the job id, and every batch writes an `import.batch_committed` audit entry), checks the asset out through `CustodyService` when `assigned_to` names a person (a refusal is a warning: the asset stays, unassigned), and never changes the status of an asset that is checked out (custody owns it). Matching is repeated at commit time, not trusted from the dry run: a record that appeared meanwhile follows `on_match`; an update whose record's `version` differs from the one the dry run saw is **not applied** (`changed-since-dry-run`, the optimistic-concurrency answer to live edits); a record created by this very import as the missing parent of an earlier row adopts the cells of its own row. An update stores the values it replaced in `before_image` (import undo, v1.1, needs no migration).

Throughput came from four decisions: the audit rows, events and asset-history rows of an asset batch are collected (`context/bulk-writes.ts`: the same writers, the same rows, the same transaction) and inserted with ONE multi-row INSERT each before the savepoint is released (that is four of the six statements a created asset costs); a batch runs in **one savepoint, not one per row**, and only when a row fails or throws is the batch rolled back to that savepoint and run again row by row (each row in its own savepoint: a failing row is recorded and does not touch the others); one lookup per batch instead of per row; and `AssetsFacade.createInTx` answers with the row it just wrote instead of reading it back (three queries saved for every asset created, API included), and the tag numbering template is read once per transaction.

## 6. One worker job per batch, resumable by construction (DECISION)

`import.step` (`{ tenantId, importId }`, ids only; queue class `bulk`) is **one batch in one tenant transaction**; at its end it queues the next step **in the same transaction** (transactional enqueue, ADR 0004) or finishes the phase. The job row holds the `cursor_row`; the rows hold their results; so there is nothing in memory to lose. A step that dies (killed worker, database error, deadline) rolls back completely and pg-boss retries it (the active job expires after one minute, so a killed worker is noticed within the queue's maintenance interval; five retries with back-off); a duplicate step (a retry racing a sweep) serialises on the job row's `FOR UPDATE` and finds the work done. `import.sweep` (scheduler producer, every 5 minutes per tenant) re-queues imports that say "running" but have not moved for 10 minutes, and ends one that has been failing for six hours (`failed`, with a sentence). Cancel sets `cancel_requested`; the next step turns it into `cancelled` (rows already written stay). Every step re-checks that the requester is still an active user, that the mapping is valid and that its state is the one it expects. A worker never holds a transaction longer than one batch (1,000 rows by default, `IMPORT_BATCH_ROWS`, about three seconds), so a tenant cannot starve the pool, and `bulk` jobs yield to interactive ones in the queue.

## 7. Presets, templates and the Google Admin export (DECISION)

`GET /v1/imports/presets` lists the built-in presets with their data dictionary: **assets, people, locations, departments** (downloadable as CSV or XLSX with example rows and, in the workbook, a dictionary sheet; asset templates also carry one `cf:<key>` column per custom field) and **`google_admin_chromeos`**. Creating an import from the Google preset **creates** the Chromebook asset category and its custom fields (`os_version`, `platform_version`, `firmware_version`, `last_sync`, `annotated_location`, `org_unit_path`, `mac_address`, `ethernet_mac_address`, `ip_address`, `boot_mode`, `auto_update_expiration`) when they do not exist (`catalog:manage` is required then) - an explicit act, not a side effect of a dry run. The preset maps by header text (serial number -> serial, Asset ID -> tag, Status -> status label by state type, Model, OS/platform/firmware versions, Last sync, User -> the person the device is checked out to, Org unit path -> location, MAC addresses, Device ID -> external id with source `google_admin`), matches **by serial** and **updates** on re-import, so importing the same file twice creates nothing the second time. The column set is a best reconstruction of the Admin console export; the real anonymised file (F-09) is the acceptance test, and the synthetic sample used by the tests lives in `apps/api/test/importer/fixtures`.

## Consequences

- New contract (`[M2-W3 IMP]`): 19 operations (tag Imports: `/v1/imports`, presets and template files, analyse, apply a template, distinct values, dry run, rows, error report CSV, commit, cancel, `/v1/import-templates`), problem codes `import-wrong-state`, `import-stale-dry-run` (now emitted), `import-quota-exceeded`. The placeholder schemas of the first drafts (`snipe_it` source, `dry_run_queued`... states) are gone; the Snipe-IT importer (M5) adds its source when it exists.
- New tables `import_job`, `import_row`, `import_template` (migration 0110) with the tenant conventions, isolation tests (`test/isolation/imports-isolation.e2e.test.ts`) and route-replay cases for every route; permissions are the catalogue's `import:read` (list, get, templates, presets) and `import:run` (everything that changes anything and everything that shows rows); the entity's own write permission and, for created references, the catalogue's, are checked when the dry run and the commit are requested.
- New queues `import.analyze`, `import.step`, `import.sweep`; notification `import.completed` is wired (subscription in `notifications/subscriptions.ts`).
- Dependencies: `yauzl`, `saxes`, `fflate`.
- Not built: import undo (v1.1; the before-images are stored), accessories, consumables, models and categories as import targets, AI-assisted mapping (Could), per-row progress push (the wizard polls), the Snipe-IT source (M5).
- Performance and the measured numbers are in `docs/STATUS.md` and `docs/AUDIT.md`; the nightly gate is `apps/api/test/perf/import-perf.e2e.test.ts`.

## Amendment, 2026-11-24 (ED-25)

The retention job exists: `import.sweep` removes the rows, samples, value map and uploaded file of imports that finished
more than `IMPORT_ROW_RETENTION_DAYS` (default 30) ago (migration 0141, `import_job.data_purged_at`). The sweep takes its
clock as a parameter, so the six-hour give-up and the purge are tested without waiting.
