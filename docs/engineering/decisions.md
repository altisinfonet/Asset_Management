## ED-01. `person` is separate from `user_account`

- **Decision.** The assignee of a custody period is a `person` (employee, student, contractor, external), which may have no login. `user_account` holds only login-capable accounts; a person optionally links to one (`person.user_id`, unique). `assignment.person_id` targets a person, never a user. One person row is auto-created for each user.
- **Rationale.** The education case has thousands of students who never log in; forcing them into the authentication tables would bloat them and blur the security boundary. Directory sync (SCIM, Entra/Google in v1.1/v2) naturally writes people, not accounts.
- **Consequences.** Departs from the plan's `ASSIGNMENT.user_id` and `USER_ACCOUNT.can_login` (data_model.md section 8). Offboarding works on people (`GET /v1/people/{id}/assignments`). Disabling a user does not touch the person's custody.
- **Milestone.** M2 (tables `app.person`, `app.assignment`). Already in `schema.sql`.

## ED-02. State type `undeployable`

- **Decision.** `status_label.state_type` is one of `deployable`, `deployed`, `pending`, `undeployable`, `archived`, `lost`. `undeployable` is added to the plan's five types; "In repair" and "Broken" are seeded labels of that type.
- **Rationale.** A broken or in-repair asset must not be checkable out, but it is not archived (still owned, still in the registry) and not pending (not waiting for an event). Without the type the lifecycle module would need a second flag.
- **Consequences.** Only `deployable` assets can be checked out; opening a repair moves an asset to an `undeployable` label and completing it restores `restore_status_id`. The plan's list of state types is superseded.
- **Milestone.** M1 (`app.status_label`). Already in `schema.sql`.

## ED-03. Stocktake belongs to M3

- **Decision.** Stocktake (physical audit: a counting session over a location or category, scanned items, found/missing/unexpected outcomes) is delivered in M3 together with the Expo scanning flows. It is not part of M1 or M2.
- **Rationale.** The stocktake workflow is driven by the mobile scanner; building the tables before the client exists would freeze a shape nobody has exercised.
- **Consequences.** No stocktake tables, endpoints or permissions in this folder. `data_model.md` carries a short "Planned M3" note listing the entities. Plan 5.2 still counts stocktake as an MVP Must; it ships with M3, not M2.
- **Milestone.** M3.

## ED-04. Mobile authentication: OIDC with PKCE, short-lived access token, rotating refresh token

- **Decision.** The Expo app authenticates with the OIDC authorization-code flow with PKCE and holds a short-lived access token plus a rotating refresh token (each refresh returns a new refresh token and invalidates the old one; replay of a used refresh token revokes the whole token family). The token endpoints are added in M3. Device-scoped API keys are not used for people.
- **Rationale.** Matches architecture section 9, keeps long-lived secrets out of the app binary, and gives per-device revocation. API keys stay for integrations and scripts.
- **Consequences.** The contract today has only the session cookie and API-key bearer auth; no OpenAPI change is made now. M3 will add token and refresh endpoints and an identity table for hashed refresh tokens (see the "Planned M3 endpoints" note in `data_model.md`).
- **Milestone.** M3.

## ED-05. Narrow DB role and pool for `identity` lookups before M4

- **Decision.** In M1 the runtime role `app_user` reads and writes the `identity` tables (no RLS, hashes and ids only) through the same pool as tenant queries. Before M4 (first real users) a narrow second role (working name `app_auth`) with its own connection pool takes over every `identity` access, and `app_user` loses its grants on `identity`.
- **Rationale.** With one role, a SQL-injection bug in a tenant query could read `identity.credential` and `identity.session` for all tenants. A second role closes that at the cost of a second pool; deferring it to M4 avoids the work while only test data exists.
- **Consequences.** The auth module must be the only code that touches `identity`, so the later split is a configuration change plus grant changes, not a refactor. Tracked as a hard gate for M4. See the tenancy section of `data_model.md`.
- **Milestone.** M1 (accepted exposure), changed in M4.

## ED-06. Audit retention, offboarding and DSAR deletion through a retention role

- **Decision.** `app_user` stays append-only on `audit_log` (and `asset_history`). Retention by plan tier, tenant offboarding purge and DSAR deletion run through a dedicated DB role (working name `app_retention`) that holds `DELETE` on those tables, is subject to RLS (it sets the tenant per run) and whose actions are themselves written to the audit log. Introduced in M4.
- **Rationale.** Keeps the append-only guarantee for the request path while still allowing the deletions the law and the pricing tiers require, without per-tier partitioning.
- **Consequences.** Not in `schema.sql` yet. Grants on the partitioned parents only, as for every other role (no grants on partitions).
- **Milestone.** M4.

## ED-07. Location scoping through `ancestor_ids`; RLS stays tenant-only; no `ltree`

- **Decision.** A role assignment scoped to a location (`scope_type = location`) is enforced by the repository layer using `location.ancestor_ids` (`ancestor_ids @> ARRAY[<id>]`, GIN-indexed with `tenant_id` first). Row-level security stays tenant-only. `ltree` is not used for now.
- **Rationale.** Keeps the isolation-critical policy trivial and uniform; the array column is trigger-maintained and fast enough for the expected depth and size (architecture 5.1).
- **Consequences.** Every repository query on a location-scoped resource must apply the scope; this is covered by `PolicyService` tests, not by the database. Revisit `ltree` only if subtree queries become a measured bottleneck.
- **Milestone.** M2 (`app.location`). Already in `schema.sql`.

## ED-08. No database-side `uuidv7()` defaults; PostgreSQL 16, 17 and 18

- **Decision.** Cloud runs PostgreSQL 18; the self-hosted edition supports bring-your-own PostgreSQL 16 and 17. Every `DEFAULT uuidv7()` is removed from `schema.sql`. Ids are always generated by the application as UUIDv7 and passed in the INSERT. `schema.sql` uses no other PostgreSQL 18 feature and is tested on 16, 17 and 18.
- **Rationale.** `uuidv7()` exists only in 18. One schema for every deployment avoids a second migration track.
- **Consequences.** SQL-side inserts and seeds must supply ids. `app.provision_tenant` seeds its rows with `gen_random_uuid()` (v4, PostgreSQL 13+), which is fine because nothing relies on seed ids being time-ordered. `app.schema_lint()` has a new rule that fails the install if a `uuidv7()` default reappears. `asset.label_code` keeps its `gen_random_uuid()` default (13+). Features used and their minimum versions are listed in the `schema.sql` header.
- **Milestone.** M1 (schema baseline).

## ED-09. `asset_history` partitioned monthly from day one

- **Decision.** `app.asset_history` is range-partitioned by month on `at`, with a default partition, under the same rules as `audit_log`: `app_user` holds `SELECT, INSERT` on the parent only; every partition has `FORCE ROW LEVEL SECURITY` and the tenant policy and no grants; no `ALTER DEFAULT PRIVILEGES`. The primary key is `(id, at)`.
- **Rationale.** It is the highest-volume table after the audit log (every status, location and custody change); converting a populated table to partitioned later is a painful migration.
- **Consequences.** The old `UNIQUE (tenant_id, id)` is gone (a unique key on a partitioned table must contain the partition key, and nothing references the table). One factory, `app.ensure_partitions(from, months)`, creates both tables' partitions (it replaces `ensure_audit_partitions`); the maintenance job must run it monthly. Retention for this table falls under ED-06.
- **Milestone.** M2.

## ED-10. Import and integration credentials in `integration_connection`

- **Decision.** Credentials for imports and integrations (for example the Snipe-IT URL and API token) are stored envelope-encrypted in an `integration_connection` table, not in `import_job.options`.
- **Rationale.** Secrets must not sit in a plain jsonb column that appears in exports, logs and API responses.
- **Consequences.** Until M5 the Snipe-IT importer is the only consumer and `import_job.options` must not be used for tokens. Recorded only; no DDL now.
- **Milestone.** M5.

## ED-11. Accessory partial returns via `quantity_returned`

- **Decision.** `assignment` gets `quantity_returned integer NOT NULL DEFAULT 0`. A partial return of an accessory increments it on the same row, which stays open; the return that makes `quantity_returned = quantity` also sets `checked_in_at`. Constraints: `0 <= quantity_returned <= quantity`, and `(checked_in_at IS NULL) = (quantity_returned < quantity)`. A trigger rejects changing `quantity` and decreasing `quantity_returned`. Outstanding units are `quantity - quantity_returned` (stock check and `v_accessory_availability`). An asset (quantity 1) closes with `quantity_returned = 1`. The accessory check-in request accepts `quantity`.
- **Rationale.** One row per custody period is kept (no close-and-reopen churn, stable assignment ids for the history and attachments).
- **Consequences.** `Assignment` in the OpenAPI contract has `quantity_returned`. Each partial return is recorded in the audit log, since the row only keeps the running total. Application code that closes an assignment must set both columns in the same UPDATE.
- **Milestone.** M2.

## ED-12. Asset tags are never reused

- **Decision.** The unique index on `lower(asset_tag)` covers archived assets, so a tag is never reassigned, even after a retention period. `app.next_asset_tag` only moves forward.
- **Rationale.** Printed labels and history stay unambiguous; a reused tag could make an old label resolve to a different asset.
- **Consequences.** To re-tag, create a new tag. No reuse job is built.
- **Milestone.** M1 (already in `schema.sql`).

## ED-13. Custody responses return the asset and the assignment

- **Decision.** `POST /v1/assets/{id}/checkout`, `/checkin` and `/transfer` return the updated asset (with its new `ETag` in the response header) together with the assignment (`{asset, assignment}`; transfer adds `transfer`). The loaner-pool check-out returns the same shape, because the client may not know which pool member was chosen.
- **Rationale.** Clients chain the next call (for example a check-in right after a scan) without re-fetching the asset, and always hold a current `ETag`.
- **Consequences.** New schema `CustodyResult`; `TransferResult` now includes `asset`. The accessory check-out and check-in keep returning the assignment alone (there is no asset ETag involved). Client code written against the earlier draft (bare `Assignment`) must read `assignment` from the body.
- **Milestone.** M2.

## ED-14. Auth contract completion (2026-11-18)

- **Decision.** The contract now covers every auth screen the web team built, plus the admin operations the M1-AUTH backlog implies (18 operations, 114 -> 132 on 82 paths).
  - Password reset: `POST /v1/auth/password/forgot` (always 202, no account enumeration), `POST /v1/auth/password/reset` (204; 404 `token-invalid`, 410 `token-expired`, 422 at `/password`; revokes every session).
  - Invitations: `GET /v1/auth/invitations/{token}` (`InvitationInfo`), `POST /v1/auth/invitations/accept` (returns `LoginResponse`; 404 `invitation-not-found`, 410 `invitation-expired`), admin `POST /v1/users/{id}/invitation/resend` and `DELETE /v1/users/{id}/invitation`.
  - MFA (TOTP): `POST /v1/auth/mfa/enrol`, `POST /v1/auth/mfa/enrol/confirm` (ten recovery codes, once), `POST /v1/auth/mfa/recovery-codes/regenerate` and `DELETE /v1/auth/mfa` (both need password or TOTP in the body; wrong value is 403 `reauth-failed`, never 401; disable is 403 `mfa-required-by-policy` when the tenant enforces MFA), admin `DELETE /v1/users/{id}/mfa`. Secret-bearing responses are never stored for idempotent replay, so these operations take no `Idempotency-Key`.
  - Sessions: `GET /v1/auth/sessions`, `DELETE /v1/auth/sessions/{id}` (409 `cannot-revoke-current`), `DELETE /v1/auth/sessions` (all others), admin `GET /v1/users/{id}/sessions` and `DELETE /v1/users/{id}/sessions/{session_id}` (M1-AUTH-03: user and admin can revoke).
  - Search: `GET /v1/search?q&types&limit` returns `{data:[{type,id,label,sublabel,href_hint}]}`, filtered per type by the caller's permissions. M1 returns asset, model and category only; person and location are accepted but empty until M2.
  - `GET /v1/auth/me` gains `mfa_enrolment_required`, `session` (`idle_expires_at`, `absolute_expires_at`; null for API keys) and `tenant.branding` (`logo_url`, `accent_color`, both null until M4+).
  - `GET /v1/auth/password-policy` (public) and schema `PasswordPolicy`: min length 12, max 128, no composition rules, breached-password check (bundled local list always; optional online k-anonymity provider).
  - Problem codes: a catalogue of every `code` (root `x-problem-codes`, schema `ProblemCode`), and each error response lists its own codes in `x-problem-codes`.
- **Rationale.** The web screens were built against proposed shapes; fixing them in the contract lets the web and API sides converge without a later rename, and the code catalogue makes error handling testable. Re-authentication failures are 403, not 401, so clients keep `401` for "session gone".
- **Consequences.** (1) The contract keeps the codes the platform code already emits: `validation` (not `validation-failed`), `idempotency-key-reuse` and `too-many-requests` (not `rate-limited`), plus `unauthorized` for a generic 401. (2) New permission `search:read`, granted to every built-in role, for `GET /v1/search`; self-service auth operations carry `x-self-service: true` instead of `x-permission` (the role matrix test must whitelist them). (3) `schema.sql` has no table for password-reset tokens yet: M1-AUTH-05 needs `identity.password_reset_token` (hash PK, tenant_id, user_id, expires_at, used_at), mirroring `identity.invitation_token`; not added here. Tenant branding and the MFA-enforcement flag live in `app.tenant.settings` (jsonb), so no DDL. (4) Revoking an invitation archives the never-activated account; resend replaces the token.
- **Milestone.** M1 (M1-AUTH-02 to 07); branding values M4+.


## ED-15. Locations, people and custody as built (M2 wave 1)

- **Decision.**
  - **People.** Every login account has exactly one `person`, created (or linked, when an unlinked person with the same email exists) by a database trigger on `user_account`, so every code path that creates a user gets it. There is no separate "link a person to a login" endpoint: the link is made by email when the account is created. Deactivating a person who still holds assets is `409` with `usage.open_assignments` unless the update carries `force: true` and a `reason` (stored in the audit trail only); an inactive person cannot receive assets; a person with a login account cannot be archived.
  - **Locations.** At most ten levels (`depth <= 9`); a move rewrites the subtree in the database (trigger) and is serialised per tenant by an advisory lock; archiving is refused with counts of children, assets, people and open assignments. `asset_count` includes descendants and is computed per request.
  - **Custody.** Check-out, check-in and transfer lock the asset row, answer `{asset, assignment}` (transfer adds `transfer`) with the asset's new ETag, require an `Idempotency-Key` and accept an optional `If-Match`; the asset row is always touched so its ETag changes with every custody change. Only a `deployable` asset can be checked out (new problem code `asset-not-deployable`; `asset-already-checked-out` and `asset-not-checked-out` are now emitted). Lost assets cannot be checked out; marking an asset lost closes its open custody; disposal sets an archived-type status, archives the asset and records reason, date and note (`Asset.disposal`); restoring a disposed asset clears the record. The allowed action per state is one table (`registry/asset-actions.ts`), used by the services, by `scan/resolve` (`allowed_actions`) and by the state-machine test.
  - **History.** `asset_history` is written in the same transaction as every change of an asset (created, updated, status and location changes, custody, archive and restore, lost and found, disposal) with the actor (user, or API key by name). Two custody events carry attachment ids only as ids (no existence check until the attachments service meets this branch).
  - **Contract additions** (all in `gen.mjs`): `POST /v1/assets/{id}/move`, `POST /v1/assets/bulk-move`, `/dispose`, `/mark-lost`, `/mark-found`, `GET /v1/people/{id}/history`; `asset_count`, `direct_asset_count`, `child_count` on `Location`; `assets_held` on `Person` and `force` / `reason` on `PersonUpdate`; `overdue`, `attachment_ids`, `checkin_attachment_ids`, `asset_tag`, `asset_name` on `Assignment`; `overdue` on `AssignmentSummary` and as an asset filter; `disposal` on `Asset`; `asset_tag` on `HistoryEvent`; the asset filters `include_sublocations`, `assigned`, `assigned_person_id` and `overdue` are live; search returns people and locations.
- **Rationale.** The first drafts left these rules to the implementer; pinning them keeps the web and mobile clients, the importer and the later waves (accessories, loaners, repairs) on one behaviour.
- **Consequences.** Not built (reported to the integrator): default location on models and categories (M2-LOC-02 mentions it, the contract has no field), location scoping of roles (M2-LOC-03, last by plan), an explicit person-to-login link action. The accessory and loaner foreign keys on `assignment` and the attachment validation are left to the integrator (see `data_model.md` 3.6.1). Update: the attachment validation was done in wave 1b and the accessory foreign key and stock trigger in wave 2 (migration 0080, ADR 0008); only the loaner foreign key is open.
- **Milestone.** M2.

## ED-16. Editing a location: `kind` is free, address limits are named on their field

- **Report.** "Location edit for site [type]: at edit time I got an error but right now I did not get it." Reproduced against the real stack: only a **site** shows the address fields, and an address value over its limit (typically a country name instead of the two-letter code) is a `422` whose pointer is `/address/country`. The edit dialog matched pointers to fields by name only, so it could not place that pointer and showed the generic "The request body failed validation (1 problem)" with no field marked; the same edit with a valid value (a two-letter code, or the field left empty) saved, hence "right now I did not get it". No `500` exists on any edit path: every scenario of the report (rename, change of kind, move, duplicate name, stale ETag, archived location, role) was replayed against the API and answers with a documented 2xx / 4xx.
- **Decision.**
  - **`kind` is editable at any time** and there are **no rules between `kind` and the tree**: a site may have a parent (a campus of sites, a site inside a region location), a room may be a root, any kind may have children and assets, changing the kind never moves, archives or recounts anything and is audited as an ordinary update. The only structural rules stay the ones that protect the tree: no cycle (`422`, `/parent_id`, code `cycle`), at most ten levels (`too-deep`), a live parent, a name unique among the live children of a parent (`409`, `/name`).
  - `address.country` must be exactly two letters (ISO 3166-1 alpha-2) and is stored upper-case (`no` is saved as `NO`); every address member has its documented length limit and a violation is a `422` on `/address/<member>`.
  - The generic form dialog (`FormDialog`) maps a nested pointer to the field that lists it (`pointers`), checks the field limits and custom rules before it calls the server (message names the field and the limit), lists a problem that matches no field in the banner instead of hiding it, and answers a `412` with "Someone saved this before you" and a **Reload latest** action that reopens the form with the other version.
  - Changing a site to another kind keeps its address (the address fields are hidden, not cleared; change it back and it is there), and an edit keeps `address.line2`, which the old form silently dropped.
- **Rationale.** The error was a message-quality bug, not an API bug; the fix puts the message on the field and stops the form from losing data. Keeping `kind` free avoids inventing hierarchy rules nobody asked for; the database has none either.
- **Consequences.** `Address.country` gets `pattern: ^[A-Za-z]{2}$` in the contract. Stored addresses written before this with a longer country value are still readable and are re-validated only when edited.
- **Milestone.** M2 (backlog M2-LOC-05).

## ED-17. Managed departments replace the free-text department

- **Decision.**
  - A tenant table **`app.department`** (`name` unique among live rows ignoring case and padding through the stored key `name_key`, optional `code` unique likewise, `description`, optional `manager_person_id`, `archived_at`, `version`) with the tenant conventions (FORCE RLS, composite FKs). People get `department_id`, **assets get an optional `department_id`** (owning / cost-centre department; the plan lists CostCenter / Department as an allocation dimension of Asset; the location stays where the asset is).
  - **Migration 0100** creates one department per distinct trimmed, case-insensitively deduplicated free-text value per tenant (most used spelling wins) and links the people without changing their version. `person.department` (text) is **kept one release as a deprecated, unused column** (nothing reads or writes it; the person read model derives `department` as the name of the linked department) and dropped later; it is not dropped now so that a rollback of the application does not lose the old values.
  - **API.** `/v1/departments` (list with `q`, counts of live people and assets, create, get, patch with `If-Match`, archive). Archiving a department that live people or assets still use is a `409` with `usage` (`people`, `assets`) unless `reassign_to=<id>` moves them to another live department in the same transaction (the merge). `department_id` is a filter of the people and asset lists, a field of both read models, writable on person create / update, asset create / update / bulk update / clone, and `expand=department` embeds it in an asset; the people and asset CSV exports carry the department name. A `department` key on person create / update is a `422` (strict bodies).
  - **Permissions.** `department:read` for every built-in role, `department:manage` for the Asset manager (and the Administrator through `*`); migration 0100 updates existing tenants and replaces `app.provision_tenant` from its definition in 0094.
  - **Web.** Settings -> Departments (list, create, rename, archive with usage message, merge), a type-ahead `DepartmentPicker` on the person form, the asset form and the bulk edit, a department column and filter on People and Assets, and the department on both detail views.
- **Rationale.** Free text produced "Maths", "maths " and "Mathematics" as three departments, which breaks every filter and report. A managed list with ids makes a rename a one-row change and a merge one call.
- **Consequences.** Breaking for API clients that wrote `department` text or filtered by `?department=`: they use `department_id`. The old column is dropped in a later migration. Departments are not yet part of the global search.
- **Milestone.** M2 (backlog M2-ORG-01, M2-ORG-02).

## ED-18. The import as built (M2 wave 3)

- **Decision.**
  - **One `import_row` per file row, both phases.** The data model of the first drafts had a row per `(job, phase, row_no)`; with 100,000 rows that doubles the storage and makes "the rows left to commit" a join. The row now carries the raw cells, the typed record, the dry-run verdict (`plan`, `errors`, `warnings`, `entity_id`, `entity_version`) and the commit verdict (`result`, `result_errors`, `created_id`, `before_image`); its key is `(tenant_id, job_id, row_no)` and nothing else refers to a row. The file is read once, at analysis; every later phase works from these rows.
  - **States** `draft, uploaded, analyzing, analyzed, mapped, dry_running, dry_run_done, committing, completed, failed, cancelled` replace the placeholder set of the contract (`dry_run_queued ... committed`). The `import_job` CHECK still says "no commit without a dry run digest"; the digest now also covers the value map and every row's plan.
  - **Sources and entity types.** `csv`, `xlsx` and `google_admin_csv`; `asset`, `person`, `location`, `department`. `snipe_it` is removed from the contract until M5 builds it (its credentials belong in `integration_connection`, ED-10); accessories, consumables, models and categories are created as **references** of an asset import, not imported as such.
  - **A dry run runs the real validators.** Assets call the facade with `dryRun: true` (it stops before the first write); people, locations and departments run their service in a savepoint that is always rolled back. Nothing the dry run does can disagree with the API.
  - **Matching** (`match_on`: tag, serial or external id; `on_match`: skip, update, error) is decided again at commit time; an update never overwrites a record whose `version` moved since the dry run (`changed-since-dry-run`); an asset that is checked out keeps its status.
  - **One worker job per batch**, queued by the previous batch in its own transaction; resumability is the cursor on the job plus the results on the rows (ADR 0010 section 6). `import.sweep` wakes a job that lost its worker.
  - **References** are resolved by name (ignoring case and padding) after the value map; `create` is the default policy for category, manufacturer, model, location, department and vendor, `must_exist` for status labels (never created) and people. Creating the Chromebook category and fields is part of **creating** a Google preset import, not of its dry run.
  - **Contract.** Tag `Imports` is rewritten in `gen.mjs` (block `[M2-W3 IMP]`): jobs, analysis, apply-template, values, dry run, rows, error report (`errors.csv`), commit, cancel, presets and their template files, saved mapping templates; new problem codes `import-wrong-state` and `import-quota-exceeded`; `import-stale-dry-run` is emitted. Attachments already accepted `import_job` / `import_file`.
  - **Upload sniffing** accepts UTF-16 (BOM) and Windows-1252 CSV for `import_file` attachments (decoded for the markup check only).
- **Rationale.** The drafts were written before the facades, the job queue and the files pipeline existed; the pieces they assumed (a staging area per phase, a worker that holds a transaction per phase) do not fit a pooled, multi-tenant system. The built design keeps the invariants (mandatory dry run, writes only through facades, audit with the job id, before-images stored) and drops the assumptions.
- **Consequences.** The web agent's wizard talks to the replaced contract (the old operations had no implementation). `import_row.raw` is tenant data (ED-19). Rolling an import back is still v1.1. A tenant may run at most `IMPORT_MAX_CONCURRENT` (2) imports at once and `IMPORT_MAX_ROWS` (100,000) rows per file.
- **Milestone.** M2 (backlog M2-IMP-01..07).

## ED-19. What an import keeps, who may read it, and how files round-trip

- **Decision.**
  - **Permissions.** `import:read` (held by every built-in role) lists and shows imports, presets and saved templates: counts, mapping, options, the column profile. Everything that shows rows (`rows`, `values`, the error report) or changes anything needs `import:run`; `GET /v1/imports/{id}` answers everybody with the shape of the file (headers, counts, mapping, options, column statistics) and only to `import:run` holders with the cells the file contains (the 50 sample rows, the sample values of each column and the source values of the value map). `import:run` is held by the (Administrator and Asset manager), plus the entity's write permission (`asset:create`, `person:manage`, `location:manage`, `department:manage`; `asset:update` when `on_match` is `update`; `asset:checkout` for `assigned_to`; the catalogue's, `department:manage`, `location:manage` or `person:manage` for references the import may create). They are checked when the dry run and the commit are requested; the worker acts as the requesting user and stops if that account is no longer active.
  - **What is kept.** The cells of every row stay in `import_row.raw` (unmapped columns included) with the verdicts; the file stays an attachment. Both are tenant data and may contain personal data (an import of people does). They are removed after `IMPORT_ROW_RETENTION_DAYS` (default 30) by the scheduled sweep (ED-25).
  - **Round trip with exports (ADR 0009).** A text cell of the file passes `stripFormulaGuard` (the apostrophe an export put before `=`, `+`, `-`, `@`, tab, CR), so an exported file imports to the original values; the error report goes through the export's CSV writer, so formulas in the file come back guarded. The header names of the exports (`asset_tag`, `serial`, `cf:<key>`, `path` for the ancestors of a location next to its `name`) are recognised by the mapping heuristic.
  - **Audit.** `import_job.created / updated / analysis_requested / dry_run_requested / commit_requested / cancel_requested / cancelled` (the API) and `import.analyzed / dry_run_completed / batch_committed` (one per batch) `/ completed / failed / cancelled` (the worker) are audit entries of the job; the records the import writes are audited as usual with `meta.import_job_id` and `meta.import_row` (assets, people, locations, departments; catalogue records created as references are audited by their own service without the job id, their request id is the worker job's).
- **Rationale.** Raw rows are the only way to offer "fix and re-upload" and a faithful error report; the price is retention, which is named instead of hidden. Splitting read from run keeps the 50 sample rows and counts visible to everybody who may see the registry while the file content stays with the people who import.
- **Consequences.** Retention is ED-25. The notification `import.completed` carries counts only.
- **Milestone.** M2 (backlog M2-IMP-01, M2-IMP-04).

## ED-20. Loaner pools: a pool is a set of assets with loan rules, a loan is an assignment with a pool

- **Decision.**
  - **Model.** Tables `app.loaner_pool` (name unique among live pools through the stored key `name_key`, `home_location_id`, `default_loan_days`, `max_loan_days`, `max_loans_per_person`, `eligible_person_kinds` (empty = every kind), `owner_user_id`, `is_active`) and `app.loaner_pool_member` (primary key `(tenant_id, asset_id)`: an asset is in at most one pool) as designed in `schema.sql`, plus the foreign key `assignment.loaner_pool_id` that migration 0041 left open (migration 0120). No new entity for the loan: **a loan is an assignment with `loaner_pool_id`**; the database already requires an asset and a due date for it (`assignment_loan_due`). Everything the custody model guarantees (one open assignment per asset, asset lock, `If-Match`, history, audit, outbox) therefore holds for loans, because lending goes through `CustodyService.checkout`.
  - **Membership.** Add / remove one (`POST` / `DELETE /v1/loaner-pools/{id}/members`) or up to 100 (`members/bulk-add`, `members/bulk-remove`, per-item results). An archived asset cannot join; an asset in another pool is `409`; removal is refused while the device is on loan from the pool. A member can still be checked out the regular way (`POST /v1/assets/{id}/checkout`): that assignment has no pool and is not a loan. Archiving a pool is `409` with `usage.open_loans` while a member is checked out, otherwise it releases the memberships. The asset list filters `loaner_pool_id=<id>` and `in_loaner_pool=true|false` are live (the first used to answer `400` "not available yet").
  - **Rules** enforced when lending: the pool is active (`409 loaner-pool-inactive`), the borrower is active and of an eligible kind (`422 not-eligible`, pointer on the borrower), at most `max_loans_per_person` open loans of the pool per person (`409 loan-limit-reached`; the borrower row is locked, so two scans cannot both slip under it), the due date is today or later and at most `max_loan_days` from today (`422 in-the-past` / `exceeds-max-loan`). **The due date of a loan is the request's `expected_return`, else today (UTC) + `default_loan_days`.**
  - **Next available device** (`POST /v1/loaner-pools/{id}/checkout` without `asset_id`): the lendable member (live, `deployable`, not out) with the lowest asset tag, locked with `FOR UPDATE SKIP LOCKED`, so 50 simultaneous requests for 5 devices lend exactly 5, each device once, and the rest get `409 no-loaner-available`.
  - **Quick flows by scanning** (the API of the web screens M2-LOAN-02): `POST /v1/loaner-pools/{id}/quick-checkout` takes one borrower (`person_id`, or `borrower` = the scanned email or `employee_ref`, which is the badge / student number: people have no separate badge field) and up to 50 `codes` (label code or label URL, asset tag, exact serial: the lookup of `GET /v1/scan/resolve`, shared in `registry/asset-codes.ts`, an ambiguous serial is refused, never guessed). The borrower is validated once for the whole request; every code is then its own loan, answered per item in request order (`results[].status` and `error`, the bulk convention), and a failing item (unknown code `404`, not in this pool `422 not-in-pool`, already out, not deployable, past the limit) does not stop the others. `POST /v1/loans/return` takes up to 100 codes of any borrowers and checks each in (the device must be in a pool, optionally in `loaner_pool_id`); it moves the device to the request's `checkin_location_id`, else to the pool's `home_location_id` (when that location is still live), and an explicit `null` leaves it where it is. Both need an `Idempotency-Key` (a retry replays the stored result, nothing is lent twice); unknown codes count as misses of the scan-resolve throttle (429 once exceeded), hits never do.
  - **Extension.** `POST /v1/loans/{id}/extend` moves the due date later (not an extension: `422 not-an-extension`; past the pool's maximum counted from the day the loan started: `422 exceeds-max-loan`). It is logged: audit `loan.extended` with old and new date and the note, outbox `loan.extended`, and an asset history entry of type `updated` whose payload carries `loan_extended: {from, to, note}`. No new history event type was added, so the web timeline and the `HistoryEvent` enum do not change. The asset's ETag changes (its `current_assignment` did).
  - **Lists and dashboard.** `GET /v1/loans` (open by default; `state=on_loan,due_today,overdue,returned`, `loaner_pool_id`, `person_id`, `asset_id`, `due_within_days`, `q`, sort `expected_return` / `checked_out_at`, keyset cursors, `include_total`), `GET /v1/loans/{id}`, `GET /v1/loans/overdue` (all open asset check-outs past due, loaner or not, with the holder), `GET /v1/loaners/dashboard` (per pool: members, available, out, overdue, due today, due soon, plus totals and the latest 20 check-outs and returns). The pool resource itself carries the live counts. All counts are computed per request; "today" is the UTC date.
  - **Contract.** Tag Loaners, 18 operations (the pool CRUD, five member operations, `checkoutLoaner`, `quickCheckoutLoaners`, `listLoans`, `getLoan`, `extendLoan`, `listOverdueCheckouts`, `returnLoans`, `getLoanerDashboard`); schemas `LoanerPool` (new members above), `Loan`, `PersonBrief`, `QuickLoanRequest/Result`, `LoanReturnRequest/Result`, `LoanExtendRequest`, `LoanerDashboard`; `OverdueCheckout` gained `asset_tag`, `asset_name`, `holder_name`, `pool_name`; problem codes `loan-limit-reached` and `loaner-pool-inactive` (and `no-loaner-available`, which the catalogue had only in the contract, now also in the API). Permissions are the existing `loaner:read` (everybody), `loaner:manage` (Asset manager, Administrator) and `loaner:checkout` (also the Technician), no new ones.
- **Rationale.** The plan says "modelled with the existing asset and assignment tables; no new entity". Keeping the loan an assignment means the 50-way race, history, the person's offboarding checklist and the overdue filters already work; the pool only adds who may borrow, how long and how many. Per-item answers are what a scanning screen needs (a bad scan must not roll back the nine good ones).
- **Consequences.** (1) `GET /v1/loans` lists loans from pools only; a regular overdue check-out shows in `GET /v1/loans/overdue` but is not a loan and raises no alert (ED-21). (2) Eligibility is by `person.kind`; "homeroom" and "device number" (the K-12 vocabulary of the backlog) are not modelled: the founder still has to confirm the labels (M2-LOAN-01). (3) Pool membership changes are audited but do not appear in the asset's history (no event type for it).
- **Milestone.** M2 (M2-LOAN-01, the API of M2-LOAN-02 and M2-LOAN-04).

## ED-21. Loan alerts, the tenant day and the custody settings

- **Decision.**
  - **The job.** Queue `loan.alerts`, one job per active tenant per day (singleton-keyed like the digest). It looks at open loans of loaner pools only and emits one outbox event per loan and state: `loan.overdue` (payload ids and counters: assignment, asset, person, pool, `daysOverdue`, `alertDate`) and `loan.due_soon` (`dueOn`). Subscriptions in `notifications/subscriptions.ts` turn them into the existing `loan.overdue` / `loan.due_soon` notification types (in-app, email immediately by default; every user can switch them off or to the digest in their preferences, an administrator can switch a type off or re-address it by role).
  - **Once per loan and state is a database fact.** The job first writes `app.loan_alert` (unique per loan and due date for `due_soon`, per loan and day for `overdue`) and emits the event only when its insert won. Running the job twice a day, a retry and two scheduler replicas cannot notify twice; the notification dedupe key repeats the rule for a redelivered event. **Overdue repeats once per day** while the loan is out (M2-LOAN-03: "once per loan per day with escalating copy"; the text adds a line from 7 and from 14 days). **Due soon** fires once per loan and due date, `loan_reminder_days` before it (default 2, 0 = no reminder), and an extension (new due date) re-arms it.
  - **Recipients.** The borrower when the person has a login account (a person without a login cannot be notified: there is no mail to non-users), and for overdue also the pool's owner (`owner_user_id`) when it has an active one, else every user who holds `loaner:manage`. Due-soon reminders go to the borrower only. A returned loan is never alerted (the subscription re-reads the assignment).
  - **The tenant day is UTC.** There is no tenant time zone setting yet (`user_account.timezone` is a per-user display preference), so "today", "overdue", "due today" and the job's day are all the UTC date, in the lists, the dashboard, the counts and the job. The job takes `today` as a parameter, which is how the tests advance the clock; a tenant time zone would be one setting read in one place.
  - **Custody settings (M2-LIFE-09).** `GET` / `PUT /v1/settings/custody` (tag Custody; read `catalog:read`, write `catalog:manage`, the permission the other settings use: the backlog's `catalog:write` does not exist), stored in `app.tenant.settings.custody`, versioned with the tenant row, `ETag` / `If-Match`, audited (`tenant_settings.custody_updated`). Members: `default_expected_return_days` (null or 1-366) and `loan_reminder_days` (0-30, default 2); PUT replaces both. **The API never applies `default_expected_return_days`**: it is the number the check-out and transfer dialogs pre-fill (today + N days), as the LIFE-09 criteria say; a check-out without `expected_return` stays open-ended. The default of a *loan* is the pool's `default_loan_days`.
- **Rationale.** A scheduler that only "usually" runs once would notify twice after a crash, so the guard is a unique index, not a clock comparison. Alerting only pool loans keeps the existing regular check-outs (which may carry old due dates) from suddenly mailing people every morning.
- **Consequences.** (1) The `loan.alerts` queue is created by the migrate step (catalogue change). (2) Moving the "tenant day" to a time zone later changes `todayUtc()`, the `now() at time zone 'UTC'` in the loan queries and the job parameter, nothing else. (3) The founder may still want the tenant default to feed the pools' default (a pool without its own `default_loan_days`); not built.
- **Milestone.** M2 (M2-LOAN-03, M2-LIFE-09).
## ED-22. Asset list sorts with empty values last; linking a person and a login account

- **Decision (sorting, M2-REG-03).**
  - `GET /v1/assets?sort=` accepts `location`, `assignee` and `due`, ascending or descending. **Empty values are listed last in both directions** (an asset with no location, in stock, or with no expected return): for a person scanning a list the empty rows are noise, whichever way they sort. This differs from `name`, `purchase_date` and `warranty_end`, which keep sorting an empty value as the smallest (changing them would reorder lists people already use).
  - **Keyset paging with NULLs.** The platform `listPage` cannot page over a nullable column (a NULL cannot be compared with `>`, so it refuses a cursor that holds one). The asset list already has its own keyset (ADR 0005, section 3); a key that can be empty is now **two terms**: a boolean "is empty" flag, always ascending (`false` = has a value, so values come first), followed by the value itself in the direction the client asked for, with a constant filler (`''`, `0001-01-01`) where it is empty. The cursor carries both (text forms, full precision) and the unique `id` tiebreaker follows the client's direction, so rows without a value are ordered by `id` among themselves and every page boundary falls between two distinct tuples. The flag terms (`location.null`, ...) are internal: `?sort=due.null` is a 400. A forged cursor with a non-boolean flag is `invalid-cursor`. The binding hash includes the flag terms, so a cursor of another sort or direction is still refused.
  - **What is compared.** `location`: the full path as the table shows it (`hq > floor 2 > room 4`), lower-cased, built once per statement as ONE jsonb map `{id: path}` over the tenant's small `app.location` table (an uncorrelated aggregate; a per-asset lookup is then a key access whatever join order the planner picks: a first version joined a derived table with a correlated path subquery and, when the planner under-estimated the tenant (an RLS tenant is unknown at plan time), evaluated the path once per ASSET: 450 ms instead of 40). `assignee`: the name of the open custody's target (person display name, location name, or asset tag), lower-cased. `due`: `expected_return` of the open custody. The custody comes from a left join on `assignment_one_open_per_asset_uq` (at most one row per asset, so the join never duplicates or drops an asset). The joins are added to the statement only when the sort needs them; the label-printing selection (`selectAssetIds`) uses the same terms and joins.
  - **Performance under RLS (ADR 0005).** The key expressions use `lower()`, `coalesce` and joins, which no index can serve under RLS (not leakproof) and which cannot be indexed as a derived value in any case, so the sorts look at every live asset of the tenant: the cost is linear in the **tenant's** asset count (like `name`), independent of the page depth. To keep that cost low the statement is **two-phase**: the inner statement carries only the asset id and the sort keys and ends in a top-N heapsort for `limit + 1` rows (its scan of the assets is an **index-only scan of the existing partial indexes** `asset_created_idx` or `asset_location_idx`: the `tenant_id = ...` condition is leakproof and `archived_at IS NULL` is the index predicate, so no heap access), and only the page of ids is joined back to the full rows (an index lookup each). The first version sorted the wide rows (custom data, notes) and took 100-500 ms; the narrow version is 3-8 times faster. The assets checked out to another asset get their tag through a scalar subquery, so the whole asset table is not hash-joined for them. Materialised sort columns with triggers on assignment, person and location were considered and rejected: three more write paths to keep correct for a gain that is not needed at the sizes in the budget; revisit with the `q` search at ~500k assets per tenant. Measured with 50,000 assets in each of two tenants, 125 locations, 40 people, 40% of the assets checked out (about 20,000 open periods), through `app.inject` on the real stack (PgBouncer), 120 samples, in the full e2e suite (a database that holds hundreds of other small tenants, the state in which the planner under-estimates a big one):

- **Decision (linking, M2-USR-03).**
  - `POST /v1/people/{id}/link-user` (`{user_id}`) and `DELETE /v1/people/{id}/link-user`, permission **`user:manage`** (Administrators), optional `If-Match`, audited as `person.user_linked` / `person.user_unlinked` with an outbox event each. Both answer `200` with the person.
  - **ED-01 and ED-15 say every login has exactly one person** (a trigger makes it), so "link an existing person" cannot simply fill an empty slot. **Linking replaces the system-made placeholder**: the login's current person is archived (never deleted: assignments, history and the audit trail keep pointing at it; `user_id` is cleared first because `(tenant_id, user_id)` is unique) and the login moves to the chosen person, who **keeps every assignment and history entry**; a department the placeholder headed is headed by the linked person. The placeholder is recognised by `created_by IS NULL` (made by the trigger, the backfill, or an unlink), not by a flag: a person that somebody created or linked on purpose is never replaced silently.
  - **Conflicts (409).** `person-already-linked`: the person already has a login (the same pair again is a no-op 200). `login-already-linked`: the login's person was chosen by somebody (unlink it first). `login-person-in-use` (`usage.open_assignments`): the placeholder still holds assets: check them in or transfer them first. 422 `/user_id` for an unknown or archived account; 404 for a person of another tenant (route replay covers it).
  - **Unlinking** detaches the login from the person and **changes nothing else about the person** (assets, history, name, email stay). The login must keep exactly one person (ED-15), so a new placeholder is created from its name and email (the email is left empty while a live person uses it, the case right after the unlink). The person is not archived, the account is not disabled and nobody is signed out. The person's name and email are not synchronised at link time; a later rename of the login account renames the linked person again (ED-15 trigger).
  - `User.person_id` (always `null` until now) is filled by `/v1/users` and `/v1/auth/me`; login responses still carry `null` (no tenant transaction there).
  - **Web.** Person page: "Link to a login" (picker of login accounts, the consequence shown before the button enables) and "Unlink login" (confirmation: the person keeps everything, the login gets a new empty person). Settings -> Users: a Person column, "Link to a person" (only people without a login are offered) and "Unlink person". A refusal of the API is shown in the dialog with its own sentence.
- **Rationale.** Sorting: the cursor never has to compare NULL, and empty-last is what a person expects of a "sort by due date". Linking: the schema (unique `user_id`) and ED-01 already forbid two persons per login; replacing the placeholder is the only reading under which the backlog's "link an existing person to an existing login" is possible without a merge feature, and archiving rather than deleting keeps the history truthful.
- **Consequences.** New problem codes `person-already-linked`, `login-already-linked`, `login-person-in-use` (catalogue and contract). The sort `enum` of the asset list grew by six values. There is no person merge: two real people are never combined. An archived placeholder is visible with `?archived=include`.
- **Milestone.** M2 (backlog M2-REG-03, M2-USR-03).

## ED-23. Undo of a custody action is one guarded inverse operation

- **Decision.**
  - **Server operation, not client-composed inverse calls.** `POST /v1/assets/{id}/undo-custody` with `{assignment_id}` reverses the **last** check-out, check-in or transfer of the asset in one transaction: an inverse action, never a delete. Composing the inverse from the existing endpoints in the browser was rejected: a check-in cannot restore the previous status or location exactly, a check-out after a check-in would carry a different checkout time, the pair of calls is not atomic (a failure between them leaves a half-undone asset) and the guard "nothing changed since" cannot be expressed. The operation uses the action's history payload (`status.from_id`, `location.from`) as its source of truth.
  - **What each undo does.** Check-out: close the opened period (note "Undo of check-out") and restore the previous status. Check-in: open a **new** period for the same holder with the same due date and note (a closed period is never re-opened: `assignment_returned_state`), restore the previous status and, if the check-in moved the asset, its location. Transfer between holders: close the new period, open a new period for the previous holder, restore the location, add a reversing `transfer` row. Transfer out of stock: like a check-out. Every undo writes a `custody_undone` history event (migration 0130; summary "Undid check-out (Ana)"), an `asset.custody_undone` audit row, the outbox event and a new version of the asset. **The original event, assignment, transfer and audit rows are untouched**, so the history shows both.
  - **Guards (all inside the asset row lock).** (1) `If-Match` is **required** and must name the exact ETag the action answered with (`*` is refused with 428): any later change of the asset (edit, move, status, another custody action) is a 412. (2) `assignment_id` must belong to the **newest** history event of the asset, which must be a check-out, check-in or transfer: otherwise 409 `undo-asset-changed`; if that event is already an undo, 409 `undo-not-possible` ("already undone"). (3) The event is at most **five minutes** old, else 409 `undo-expired` (the web offers Undo for 10 seconds; the server window is wider so a slow click or a paused toast still works, and narrower than "forever" so a forgotten tab cannot reverse yesterday's work). (4) The caller needs the permission of the action it reverses (`asset:checkout`, `asset:checkin` or `asset:transfer`; the route's declared permission is `asset:checkout`), else 403. (5) What the inverse needs must still be valid: the previous holder (person active and live, location live, asset live, no cycle) and the previous status, else 409 `undo-not-possible`. Loaner custody is refused (409 `undo-not-possible`): the loaner screens own that flow.
  - **Idempotency.** The operation requires an `Idempotency-Key`: a retry replays the stored answer; a second undo with a new key finds an undo as the newest event and is refused. Concurrent undos serialise on the asset lock.
  - **Edge cases.** Asset edited, moved or touched between the action and the click: 412 / `undo-asset-changed`, the toast says "{tag} changed in the meantime, so this cannot be undone." and nothing changes. Undo of a bulk action: one call per asset (the bulk actions are already a loop of single calls); the toast reports "Undone: 3 assets are back as they were." or "n of m" with the reasons. A check-in that photographed the asset keeps its photos on the closed period. Notifications already sent for the action are not recalled.
  - **Web.** The success toast of the custody dialog (check-out, check-in, transfer; single and bulk, also the successful part of a partly failed bulk) carries the hint "You can undo this for 10 seconds." and an **Undo** action; the toast pauses while hovered or focused (Radix). It is announced politely (`role="status"`), **F8** moves keyboard focus to the notifications region (Radix default, listed in the shortcuts help) where Undo is the first control, and the result is announced by a second toast. History timeline: new event type "Custody undone" in the custody filter.
- **Rationale.** The backlog asks for "the inverse action (never a delete) so the history stays truthful" and "absent when the inverse is no longer valid"; a server operation guarded by the ETag of the action is the only way to make "the asset changed meanwhile" reliable and the undo atomic.
- **Consequences.** New problem codes `undo-expired`, `undo-asset-changed`, `undo-not-possible`; new history event type; the history payloads of check-out, check-in and transfer-from-stock gained `status.from_id` / `to_id` (older events lack them, which is why only recent ones are undoable). Scan-batch mode has its own log and no undo. Undo of an import, a bulk edit or other actions is not offered.
- **Milestone.** M2 (backlog M2-UX-02).

## ED-24. Loaner pools: loan length precedence, mail to borrowers without a login, next available device

- **Decision** (founder, 2026-11-24).
  - **Due date of a loan, in this order.** (1) the request's `expected_return`; (2) the pool's `default_loan_days`; (3) the organisation's `default_expected_return_days` (`GET` / `PUT /v1/settings/custody`); (4) 7 days. The first three are today (UTC) + N days. A derived date is cut to the pool's `max_loan_days`; an explicit date beyond it is still `422 exceeds-max-loan`. `default_loan_days` of a pool is **optional** (nullable, null = inherit; migration 0140 drops the NOT NULL and the default of 7); `max_loan_days >= default_loan_days` is checked only when both are set. The pool carries a read-only `effective_default_loan_days` (what a request without a date gets right now, resolved through 2-4 and cut to the maximum), which is what the loaner desk pre-fills. The tenant default still does **not** apply to an ordinary check-out (ED-21: that stays open-ended, the dialogs pre-fill it); it applies only to loans from a pool without its own default.
  - **Mail to borrowers without a login.** A borrower who has no login account but has an e-mail address gets the due-soon and overdue mails when the pool allows it. The setting is per pool: `email_borrowers_without_login` (boolean, nullable). **null = automatic: every kind of person except students** (employees, contractors, external people; a pupil's or student's address is not written to unless somebody decides so on purpose); **true** = every borrower with an address, students included; **false** = nobody without a login. The rule is by the **borrower's kind**, not by the pool's eligible kinds, so a mixed pool never mails a student by accident. The mail is e-mail only (there is no account for an in-app row), has no link (they cannot sign in) and uses the same text as the in-app notification. A borrower **with** a login keeps the existing path (in-app plus e-mail by their preference) and is never mailed twice. **Overdue is always also reported** to the pool owner, else the users who hold `loaner:manage`, whatever this setting says. The mail respects the notification type's tenant rule (`loan.overdue` / `loan.due_soon` switched off sends nothing) and the ledger of ED-21 (once per loan and state). Implementation: the NOTIFIER port gained `notifyEmail` (mail to addresses that are not users, tenant rule applies, no preference, no in-app row); a subscription may name `emailRecipients` next to `recipients`.
  - **Next available device** (`POST /v1/loaner-pools/{id}/checkout` without `asset_id`): the lendable member that has been **idle the longest**: the earliest `checked_in_at` of its last custody period; a device that was never lent comes first; ties go to the lowest asset tag. Locked with `FOR UPDATE SKIP LOCKED` as before, so concurrent requests still lend different devices. This spreads wear across the cart instead of lending device 1 every time.
  - **No new fields for K-12.** A student ID is the person's `employee_ref` (the scanned badge or student number), a homeroom is the person's department (or a room location), a device or cart number is the asset tag (or a custom field). Documented for admins in `getting-started.md` and `FEATURES.md`; the user guides follow in M2-DOC-01.
- **Rationale.** The founder wants the cart to work with the data schools already have, short default loans that need no setting for every pool, wear spread over the devices, and parents' and pupils' mailboxes left alone unless chosen. A per-borrower-kind default is safer than a per-pool one, and a boolean on the pool keeps the override one click.
- **Consequences.** API: `LoanerPool.default_loan_days` is nullable, new members `effective_default_loan_days` (read-only) and `email_borrowers_without_login`; a pool created without a number no longer stores 7. Clients that showed `default_loan_days` as a number use `effective_default_loan_days`. Migration 0140. Existing pools keep the number they have. The mail needs the person's `email`; people without one are simply not mailed.
- **Milestone.** M2 (M2-LOAN-01, M2-LOAN-03, M2-LIFE-09).

## ED-25. Import data retention: rows and files of finished imports are purged

- **Decision.** (ED-19 open item.)
  - **What is purged.** The scheduled `import.sweep` job (every 5 minutes per tenant, the job that already wakes lost imports) removes the content of an import that is `completed`, `failed` or `cancelled` and finished more than `IMPORT_ROW_RETENTION_DAYS` ago (default **30**, 1-3650): every `import_row` of the job (the cells of the file, the mapped records, the dry-run and commit verdicts, the before-images), the column `profile`, the 50 `samples`, the `value_map` (its keys are values of the file), and the **uploaded file** (the attachment is archived and its object deleted; `file_attachment_id` is cleared).
  - **What stays.** The job: state, filename, counts of both phases, `summary`, `mapping`, `options`, `parse`, `headers`, dates, error text, its audit trail. The records the import wrote are ordinary records and are not touched. The job gets `data_purged_at` (migration 0141, shown in the API) and an audit entry `import.data_purged` with the number of rows deleted. An import that is still open (anything not finished) is never purged.
  - **How.** Up to 5 jobs per run, rows deleted in statements of 10,000, all inside the tenant transaction of the sweep. After a purge `GET /v1/imports/{id}/rows` is empty and `errors.csv` has only its header: the web wizard says so instead of showing an empty table.
  - **Testable clock.** `ImportRunner.sweep` and `purge` take `now` as a parameter (the job passes the real clock); the sweep's six-hour give-up (an import running more than six hours is ended `failed`) and the purge are tested with an injected clock instead of rewriting `updated_at`.
- **Rationale.** The rows hold personal data of whatever was imported (people, e-mail addresses, serial numbers). Keeping them as long as the job was ED-19's stated gap. Thirty days is long enough to fix a file and re-run or to download the error report, short enough to be defensible; it is one environment variable.
- **Consequences.** A failed row can no longer be inspected after the period: download the error report first. The before-images stored for a v1.1 import rollback are purged too, so a rollback is only possible inside the retention period (to be revisited when rollback is built). Increase the variable if auditors need longer.
- **Milestone.** M2 (M2-IMP).

## ED-26. Location scoping of role assignments (M2-LOC-03)

- **Decision.** A role assignment with `scope_type = location` and `location_id` limits its holder, for the permissions of that role, to the location and its whole subtree (`location.ancestor_ids`, ED-07). Org-wide assignments behave exactly as before.
  - **Per permission.** The auth guard computes the scope of a request from the grants that give the route's permission. If any of them is org-wide (`tenant`, or `company` until company scoping ships), the request is not limited; otherwise it is limited to the union of the location subtrees of those grants. A Technician at School A who is also an org-wide Viewer reads everywhere but checks out only at School A. Self-service routes use the principal as a whole. Where a route also needs a second permission for the records it touches (an export of assets needs `asset:read`, an import of people `person:manage`, each search type its read permission, the check-in half of a forced repair `asset:checkin`, an undo the permission of the action undone), the scope is narrowed to the intersection of both scopes, so a role bundle never widens what its holder can read or change.
  - **Granting.** Nobody grants a permission wider than they hold it: assigning a role org-wide needs each of its permissions org-wide; assigning it at a location needs each of them org-wide or in a subtree that contains that location (`403` otherwise). This also stops a user widening their own scope.
  - **Org-only permissions.** A location-scoped assignment never grants `user:read`, `user:manage`, `role:read`, `apikey:manage`, `audit:read`, `catalog:manage`, `department:manage` or `notification:manage`, not even through `*`: they act on tenant-wide records that a subtree cannot bound. A scoped Administrator is therefore a location administrator. `GET /v1/auth/me` lists the effective permissions without them, and their routes answer `403` (a route is not a secret).
  - **What is inside a scope.** Assets, accessories and consumables by their `location_id`; people by their home location; loaner pools by `home_location_id`; loans, custody records, repairs and attachments through their asset (or accessory, consumable, person, location); the locations of the subtree themselves (not their ancestors). The tenant-wide catalogue (categories, manufacturers, models, status labels, vendors, custom fields, departments, companies, label and import templates, settings) stays readable by everybody with the read permission.
  - **No location means outside every scope.** An asset, person, stock item or pool without a location is invisible to scoped principals. Writes by a scoped principal must keep the record inside the scope: creating it without a location, setting the location to none, or creating a top-level location is `422` with code `required` (`/location_id`, `/home_location_id`, `/parent_id`).
  - **Out of scope looks like not found.** A path id outside the scope is `404`, with the same body as a missing id. Lists, counts, search and scan resolve leave the record out. A request that names an out-of-scope record as a target is refused exactly as for an unknown id (`422` `not-found` at the field). This covers check-out, transfer and check-in to a person, location or asset outside the scope; moving an asset, a location or a person's home out of the scope; repair performers; pool members and borrowers (also a borrower found by email or badge); label batches; attachments; the default location and the value mapping (by id) of an import; the id references a saved view's filters are checked against (the view warns `not-found`, as for an unknown id). The one unavoidable signal is uniqueness: an asset tag, serial or person email that is taken outside the scope is still a duplicate (`409` / `422`), because uniqueness is tenant-wide. It says that a value is used, not where or by what.
  - **Bulk actions with mixed rows.** Each row is checked on its own, as before (one savepoint per item): rows outside the scope fail as `404` in the per-item results, the others succeed.
  - **Loan returns** put a device back at its pool's home only when that place is inside the caller's scope; otherwise it stays where it is.
  - **Exports and imports.** The scope of the requester at request time is stored on the job (`export_job` and `import_job` `location_scoped` + `location_scope`, migration 0150), and the worker applies exactly that scope. A CSV never holds a row the requester could not list. An import matches existing records inside the scope only, resolves location paths from the scope roots down and people inside the scope, and refuses targets outside it. The exports, imports and label batches of a scoped principal are its own only, because they carry the content of whatever they touched. Department imports and the "create missing" of catalogue references need org-only permissions and are refused.
  - **Dashboard and counts.** Totals (`include_total`), location roll-ups, department counts, pool counts and the loaner dashboard count inside the scope only, so a scoped user's numbers are smaller than an administrator's.
  - **The holder of an in-scope asset (accepted, founder 2026-11-25).** An asset inside the scope shows who or what holds it even when the holder is outside the scope: the holder's id and name in `current_assignment`, in the asset's history and custody list, and in the assets CSV export. The holder's own record stays `404` (`GET /v1/people/{id}` and its sub-resources), and the holder is absent from the people list and search. Filtering the in-scope assets by that holder (`GET /v1/assets?assigned_person_id=<id>`) returns the in-scope assets the person holds, consistent with what each asset shows; it never returns their assets outside the scope.
  - **History.** The timeline of an asset inside the scope is shown whole; it may name a place or a holder outside the scope (as text). A person's timeline and custody list show only the items inside the caller's scope.
  - **Location filters.** A location filter selects inside the scope: `location_id=<id>` with sub-locations returns the in-scope part of that subtree. A location outside the scope that is not above it returns nothing, like an unknown location. An ancestor of a scope root (which the principal sees by name in `/auth/me`) returns the in-scope locations below it.
  - **`GET /v1/auth/me`.** `location_scope.locations[].path` names the ancestors above each scope root (for example "District / School A"): the principal is told where its subtree sits, by name only. The ancestors themselves stay `404`.
  - **Scan resolve.** `allowed_actions` lists an action only when the permission it needs reaches the asset (that permission's scope contains the asset's location), not merely when the principal holds the permission somewhere.
  - **Saved views** store filters only. A shared view applied by a scoped user returns scoped results (see Location filters).
  - **Notification recipients.** A user whose scope (as a whole) does not contain the location of the subject (asset, accessory, consumable) is not told, except the holder the event is about (their own check-out or loan). Personal notices (export, import, label batch, infected upload) go to the requester as before. Webhooks stay tenant-level (architecture item 14).
  - **Enforcement: an application-layer predicate, not RLS.** The guard puts the scope on the request context, and every `withTenantTx` of the request inherits it. A job acting for a user sets it explicitly; a nested call or a second permission narrows the scope to the intersection (computed from `ancestor_ids`), never widens it. The repository layer applies `location_id IN (SELECT id FROM app.location WHERE ancestor_ids && <roots>)`, or the same as `IN (<ids>)` through Prisma, on every scoped read and write path: the asset load, lock, list, count and selection helpers, the loads of locations, people, stock, pools, loans, repairs and attachments, and the target lookups. Row-level security stays tenant-only (ED-07, architecture A1).
- **Rationale.** Scoping in RLS would need a second per-request setting and policies that join `location` on every table. The array operators such a policy needs (`&&`, `@>`) are not leakproof, so under RLS they cannot drive an index (ADR 0005): every scoped query would scan the tenant, and tenant isolation, the property that must never fail, would get a more complex policy. In the application layer the subtree is resolved against the tenant's small location table, and the hot tables are filtered with plain uuid equality (`IN`), which is leakproof and uses the existing `(tenant_id, location_id)` btree indexes. No materialised path or `ltree` key is needed, so ED-07 stands. The price of the application-layer choice is that a forgotten predicate leaks inside a tenant. The scoped route replay (`apps/api/test/isolation/scope-replay.e2e.test.ts`) covers that: it replays every route as a location administrator against another site's records, fails on any response that contains their markers or any write to them, and fails when a new route has no scoped case. 404 rather than 403, because a 403 confirms that the id exists.
- **Consequences.** Migration 0150 (the job scope columns). `Me.location_scope` (null for org-wide principals) drives the web "Scoped to" indicator, and the users screen sets the scope per assignment. Company scoping is still not enforced (accepted, behaves like `tenant`). Not filtered, by design: the tenant-wide catalogue, and the place names in an in-scope asset's own history.
- **Milestone.** M2 (M2-LOC-03; closes the scoping criterion of M2-LIFE-06).
